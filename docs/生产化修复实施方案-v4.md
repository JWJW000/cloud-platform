# 云端自动化平台生产化修复实施方案 V4

> 编写日期：2026-08-22  
> 适用目录：`cloud-platform/`  
> 文档性质：生产阻断缺陷修复任务书、接口约束、事务设计、测试计划与交付验收基线  
> 实施对象：负责下一轮代码修改的 Agent  
> 前置基线：`生产化修复实施方案-v3.md` 及 V3 实现后的代码检查结果  
> 当前结论：格式化、Clippy 和前端构建可以通过，但系统仍存在部署、数据一致性、重启恢复和安全阻断问题，不得直接用于生产

---

## 1. 文档目的

本文件不是泛化建议，而是下一轮实现必须逐项完成的修复合同。实施 Agent 必须：

1. 保留当前已经正确工作的模块，做最小范围增量修复；
2. 先补能复现问题的失败测试，再修改实现；
3. 所有状态迁移、并发更新和恢复裁决都必须有明确的不变量；
4. 任何关键路径不得使用“失败后继续”“缺少配置时自动降级”或“测试未配置时显示通过”；
5. 每个修复项必须同时提交实现、自动化测试、配置示例和文档；
6. 未满足本文件验收标准，不得在 `实现进度.md` 中标记为“完成”。

本轮完成后，系统至少应稳定支撑：

- 约 5 台异地物理 Worker；
- 每台 Worker 由管理员配置不同槽位数；
- Worker 通过公网稳定连接云端 Master；
- Worker 通过局域网直接把文件写到同一台 NAS；
- 同一本书同一格式全局只保存一份；
- 一本书整个下载过程固定使用同一个 Webshare 出口 IP；
- Worker、Master 或网络重启不会导致重复下载、覆盖文件、错误续租或任务永久卡死；
- 管理平台会话、证书、代理凭据和操作日志达到生产安全基线。

## 3. 不可变业务约束

### 3.1 全局任务与文件

1. 图书是全局主数据；
2. 同一本书同一格式只存在一个全局任务；
3. 多个批次可引用同一个全局任务；
4. 取消某个批次不得取消其他活动批次仍需要的任务；
5. 同一本书同一格式的 NAS 最终相对路径必须唯一；
6. 已存在同路径同哈希文件视为幂等成功；
7. 已存在同路径不同哈希文件必须停止自动处理并产生严重告警；
8. 任何 Worker 都不得自动覆盖最终文件；
9. 已经完成最终提交的文件不得因晚到取消消息而删除；
10. Master 只保存 NAS 相对路径，绝不保存 Worker 的本地绝对挂载路径。

### 3.2 Worker 与槽位

1. Worker 数量表示物理电脑数量；
2. 槽位表示该电脑允许同时运行的浏览器执行数；
3. 本地 `requested_slots` 是设备安全上限；
4. Master 管理员配置是云端批准上限；
5. 实际可用槽位数取两者较小值；
6. 缩容、暂停和取消必须在 NAS 提交临界区之外中断；
7. Worker 进程重启后，不假设浏览器会话仍存在；
8. 只有可证明恢复的本地文件或 NAS 文件阶段才能继续，搜索和下载阶段必须安全重试。

### 3.3 代理和出口 IP

1. 继续使用 Webshare；
2. 一个执行会话从创建到关闭固定绑定一个代理记录；
3. 一本书的登录、搜索、点击、等待和下载完成使用同一会话；
4. 当前书执行中不得自动切换上游代理；
5. 代理故障应结束会话，再由 Master 分配新代理和新会话；
6. Webshare API Key 只保存在 Master；
7. Worker 只接收当前会话所需的解密后代理凭据；
8. 代理密码、API Key、节点 token、JWT 不得进入日志。

### 3.4 中文业务值

数据库、API 响应、gRPC 业务字段和日志中的业务状态必须使用中文。技术协议标识可以保留英文，例如：

- `pdf`、`epub`；
- `http`、`https`、`socks5`；
- UUID、SHA-256、IP；
- Windows、macOS、Linux；
- gRPC、JWT、TLS、Webshare。

禁止在多个模块重复手写中文阶段字符串。业务阶段和裁决必须由共享类型或 protobuf 枚举表达，展示时统一映射为中文。

## 4. 目标架构与信任边界

### 4.1 推荐的公网入口拆分

生产环境推荐使用两个域名或两个独立 TLS 入口：

```text
管理浏览器
    │ HTTPS，公开受信 Server Certificate
    ▼
admin.example.com
    ├── /api/*        → Master HTTP 8080
    ├── /api/events   → Master SSE
    ├── /              → Master 静态站点
    └── Enroll gRPC   → Master gRPC 9443（仅服务端 TLS）

异地 Worker
    │ HTTPS + Node Client Certificate
    ▼
worker.example.com
    └── OpenLink gRPC → Caddy require_and_verify mTLS
                         → 删除外部伪造指纹头
                         → 注入真实证书指纹
                         → Master gRPC 9443
```

两个入口的职责：

- Server CA：用于 Worker/浏览器验证云端服务器；
- Node CA：仅用于 Caddy 验证 Worker 客户端证书；
- 两个 CA 必须分离，不得把 Node CA 加入 Worker 的服务端信任根；
- 注册入口不要求客户端证书，因为注册前 Worker 尚无证书；
- OpenLink 入口在 TLS 握手阶段要求并验证客户端证书；
- Master 再校验节点 token、证书指纹归属、吊销状态和节点状态。

### 4.2 私有 CA 模式

如不使用公网 ACME 证书而使用 `tls internal`：

1. Caddy Server CA 根证书必须通过运维渠道预先分发给 Worker；
2. 该证书配置为 `server_ca_file`；
3. 它不能通过未受信任的注册连接首次下载；
4. 文档必须提供根证书导出、指纹核验和安装步骤；
5. Worker 首次连接前由管理员核对 Server CA SHA-256 指纹；
6. Node CA 仍然只用于客户端证书，不得复用。

### 4.3 主要威胁及控制

| 威胁 | 控制 |
| --- | --- |
| 冒充 Worker | mTLS、节点 token、证书指纹归属三重校验 |
| 伪造代理指纹头 | Master gRPC 不对公网开放；Caddy删除外部头后注入真实值 |
| 恶意 CSR | Master 覆盖主体，禁止 CA 权限，限制 SAN 和 Key Usage |
| NAS 覆盖 | 原生 no-replace 提交；能力不足时失败关闭 |
| 路径逃逸 | 相对路径组件校验、canonical containment、创建前检查 |
| 旧执行覆盖取消 | 事务内行锁、重新裁决、条件更新、检查影响行数 |
| JWT 会话绕过 | 强制 jti、令牌哈希绑定、当前用户/角色/版本查库 |
| 登录爆破和内存耗尽 | 有界双维度限流、定期清理、失败审计 |
| Webshare SSRF/残缺快照 | HTTPS 官方域名允许列表、禁止重定向、完整快照才提交 |
| 测试假绿 | CI 强制 PostgreSQL、明确跳过计数为零、真实并发测试 |

## 6. R0：先建立不会假绿的测试门禁

### 6.1 目标

在修业务代码前，先保证每项修复能被自动化测试证明。测试环境缺失必须失败，不得返回后显示 `ok`。

### 6.2 PostgreSQL 集成测试

保留 `TEST_DATABASE_URL`，但调整执行策略：

- 单元测试可以不依赖数据库；
- 文件名位于 `tests/` 的数据库集成测试在 CI 中必须设置 `REQUIRE_TEST_DATABASE=1`；
- CI PostgreSQL 服务必须运行完整迁移；
- 测试日志必须明确打印实际数据库地址的脱敏信息和迁移版本；
- CI 最终检查所有数据库测试二进制确实至少运行一个测试；
- 不得用 `return` 把缺库当成功。

推荐提供独立命令：

```bash
cargo test --workspace --all-targets
REQUIRE_TEST_DATABASE=1 cargo test -p master-server --tests -- --nocapture
```

### 6.3 CI 工作流

新增 `.github/workflows/ci.yml`，至少包含：

1. `rust-static`：fmt、Clippy；
2. `rust-unit`：无数据库单元测试；
3. `postgres-integration`：PostgreSQL 16 服务、真实迁移、强制数据库测试；
4. `frontend`：`npm ci`、真实单元测试、生产构建；
5. `dependency-audit`：Rust 和 npm 锁文件审计；
6. `worker-platform`：Linux、Windows、macOS 的 Worker 单元测试矩阵；
7. `docker-build`：构建生产镜像并对静态首页做冒烟测试。

所有 Job 必须是必需检查。任何一个失败不得发布镜像。

### 6.4 前端测试

删除固定打印成功的 `npm test`，引入实际测试框架，例如 Vitest。至少覆盖：

- 登录成功后只依赖 HttpOnly Cookie，不保存 JWT；
- 401 时清空用户状态；
- 登录失败展示中文错误；
- SSE 仅创建一个连接，退出时关闭；
- 重新登录不会累积多个 SSE 连接；
- 写操作发出正确的同源请求；
- 中文状态徽标映射；
- 批次取消确认流程。

### 6.5 R0 验收

- 删除 PostgreSQL 环境变量并设置 `REQUIRE_TEST_DATABASE=1` 时，测试必须失败；
- 配置 PostgreSQL 后，测试必须真正建 schema、迁移、执行断言和删除 schema；
- `npm test` 必须输出实际用例数；
- CI 文件存在且能在干净环境执行；
- 不允许把网络或数据库测试标成永久 `ignore`。

## 7. R1：修复生产静态资源部署

### 7.1 当前问题

镜像复制目录是：

```text
/app/web-admin/dist
```

配置却是：

```toml
web_root = "web-admin"
```

Master 从 `/app/web-admin` 查找 `index.html` 和 `/assets/*`，生产首页无法正确加载。

### 7.2 必须修改

建议将镜像内配置明确设为：

```toml
web_root = "/app/web-admin/dist"
```

同时完成：

1. Dockerfile 只复制 `dist`，不复制源码和 `node_modules`；
2. Master 启动时若配置了 `web_root` 但目录或 `index.html` 不存在，必须启动失败；
3. 静态资源请求优先读取真实文件；
4. 非 `/api` 且没有对应文件的浏览器路由回退到 `index.html`；
5. `/api/*` 不得回退到 HTML；
6. 静态哈希资源设置长期缓存，`index.html` 设置短缓存或不缓存；
7. Caddy 继续把 API、SSE 和静态流量反代到 Master，或直接由 Caddy 提供 `dist`，但只能选择一个清晰方案。

### 7.3 冒烟测试

生产镜像启动后测试：

```text
GET /                 → 200，Content-Type text/html
GET /assets/<hash>.js → 200，Content-Type javascript
GET /workers          → 200，返回 index.html
GET /api/not-found    → 404 JSON，不返回 index.html
```

### 7.4 R1 验收

- 使用最终 Docker 镜像而不是本地源码目录测试；
- 浏览器无控制台资源 404；
- 页面刷新任意前端路由不出现 404；
- 镜像中不存在 `web-admin/node_modules`。

## 8. R2：TLS/mTLS 信任链重构

### 8.1 配置模型

Worker `[master]` 配置必须明确包含：

```toml
endpoint = "https://worker.example.com"
enroll_endpoint = "https://admin.example.com"
tls_domain = "worker.example.com"
identity_file = "data/identity.json"
client_cert_file = "data/client.crt"
client_key_file = "data/client.key"
node_ca_file = "data/node-ca.crt"
# 仅私有 Server CA 部署需要；公网受信证书可不填
server_ca_file = "data/server-ca.crt"
```

字段职责：

| 字段 | 用途 |
| --- | --- |
| `client_cert_file` | Worker 向 OpenLink 出示的客户端证书 |
| `client_key_file` | 客户端私钥，只存在 Worker 本地 |
| `node_ca_file` | 节点客户端证书签发 CA 的公开证书，用于审计，不用于验证云端服务端 |
| `server_ca_file` | 私有部署下验证云端 Server Certificate 的 CA |
| `tls_domain` | 服务端证书域名校验覆盖值；通常与 endpoint 主机一致 |

### 8.2 Worker 注册通道

注册通道必须：

1. 只接受 `https://`；
2. 使用系统根或显式 `server_ca_file` 验证服务端；
3. 校验域名；
4. 不加载 Node CA；
5. 不加载客户端证书；
6. 设置连接、请求和整体注册超时；
7. 禁止证书验证失败后退化为 HTTP；
8. 注册码、CSR、返回证书错误不得记录敏感内容。

### 8.3 Worker OpenLink 通道

`worker-agent run` 启动前必须 fail closed：

- endpoint 不是 HTTPS：失败；
- identity 不存在：失败；
- client cert 不存在：失败；
- client key 不存在：失败；
- cert/key 不匹配：失败；
- 证书已过期或即将过期：失败或告警；
- 私有 Server CA 配置了但文件不存在：失败；
- 文件权限不安全且无法收紧：失败；
- Node CA 绝不能加入服务端信任根。

### 8.4 注册产物原子保存

当前顺序覆盖多个文件后再清理的方式会破坏旧身份。改为：

1. 在同一目录创建唯一临时文件；
2. 写入私钥、客户端证书、Node CA 和 identity；
3. 每个临时文件 `sync_all`；
4. 解析证书并验证：
   - 证书公钥与新私钥匹配；
   - 证书链由 Node CA 签发；
   - CN/SAN 策略符合节点证书要求；
   - 有效期合法；
5. 对已有身份先创建可恢复备份或采用目录版本切换；
6. 所有验证成功后再原子切换到新版本；
7. 失败只删除本次临时文件，不删除原有可用身份；
8. 指纹必须对证书 DER 计算，而不是对 PEM 文本计算。

推荐目录结构：

```text
data/identity/
├── current -> versions/<version>/       # Windows 可用 current.json 指针代替软链接
└── versions/
    └── <version>/
        ├── identity.json
        ├── client.crt
        ├── client.key
        └── node-ca.crt
```

### 8.5 Caddy 入口

推荐拆分入口：

- 注册/API 域名：公开受信 Server Certificate，不要求 Client Certificate；
- WorkerLink 域名：公开受信 Server Certificate，并设置 `require_and_verify` 客户端证书；
- WorkerLink 域名仅路由 `OpenLink`；
- Caddy 删除所有外部 `x-client-cert-fingerprint`；
- 只使用真实 TLS 客户端证书计算指纹；
- Master 8080/9443 只暴露在 Docker 内网，不映射公网端口。

若暂时单域名使用 `client_auth mode request`，必须同时满足：

1. Master 生产配置强制 `require_client_cert=true`；
2. OpenLink 缺失或空指纹时拒绝；
3. 代理头不可从公网保留；
4. 自动化测试覆盖无证书、伪造头、错误证书和已吊销证书。

### 8.6 证书测试矩阵

必须覆盖：

- 公网/测试 Server CA 的正常注册；
- 私有 Server CA 正常注册；
- 未信任 Server CA 注册失败；
- 域名不匹配失败；
- OpenLink 缺客户端证书失败；
- 客户端证书属于其他节点失败；
- 节点 token 错误失败；
- 证书吊销后现有链路被断开；
- 吊销后重连失败；
- 证书过期失败；
- 伪造指纹请求头不能通过；
- 原身份存在时注册保存失败，原身份仍可使用。

## 9. R3：NAS 不覆盖原子提交

### 9.1 核心原则

NAS 最终提交只能有三种结果：

```rust
enum CommitOutcome {
    Created,
    AlreadyExistsSameHash,
    ConflictDifferentHash,
}
```

不得存在“不确定但当作成功”或“锁失败后继续 rename”的分支。

### 9.2 支持策略

按平台使用原生 no-replace 能力：

- Linux：`renameat2(..., RENAME_NOREPLACE)`；
- macOS：`renamex_np(..., RENAME_EXCL)`；
- Windows：使用明确“不替换目标”的 Win32 原子移动 API，并检查 `ERROR_FILE_EXISTS` / `ERROR_ALREADY_EXISTS`；
- 支持硬链接且同文件系统时，可使用 `hard_link(temp, final)` 作为独占创建方案；
- 不允许回退到 `exists() + rename()`；
- 不允许忽略锁文件 `create_new` 的结果。

如果当前操作系统与 NAS 文件系统组合不能提供可靠的 no-replace 语义：

1. NAS 能力探测返回不支持；
2. Worker 状态进入“存储异常”；
3. Worker 不再申请下载会话；
4. 管理平台产生严重告警；
5. 不得为了继续下载而使用不安全回退。

### 9.3 启动时能力探测

除可写和剩余空间外，增加一次 no-replace 语义探测：

1. 在 NAS 隐藏探测目录创建源文件 A；
2. 创建已存在目标 B；
3. 调用正式 `commit_noreplace`；
4. 必须返回 AlreadyExists；
5. 验证 B 内容未变化；
6. 清理探测文件；
7. 记录操作系统、文件系统错误码和探测结论，但不记录敏感路径之外的信息。

能力探测应在启动时和 NAS 重新挂载后执行，不需要每个心跳执行。

### 9.4 入库完整流程

```text
下载完成
  → 校验格式、大小、魔数
  → 计算本地 SHA-256
  → 持久化“本地文件完成”现场
  → 在最终目录 create_new 唯一 .uploading 文件
  → 拷贝并 flush/sync
  → 对 NAS 临时文件重新计算 SHA-256
  → commit_noreplace
      ├─ Created → 复算最终文件 → 保存“NAS 已原子落盘”
      ├─ AlreadyExists → 计算既有最终文件 SHA-256
      │    ├─ 相同 → 幂等成功
      │    └─ 不同 → 冲突，禁止覆盖，告警
      └─ Unsupported/Error → 存储异常，保留可诊断现场
```

### 9.5 路径安全

所有目录创建必须发生在 containment 校验之后：

- 拒绝绝对路径；
- 拒绝 `..`、`.`、空组件；
- 拒绝 Windows 盘符、UNC 注入和保留设备名；
- 拒绝路径分隔符出现在叶子文件名；
- canonicalize 已存在的最近父目录；
- 确认其位于 canonical NAS 根下；
- 不跟随最终路径上的符号链接或重解析点；
- 最终路径只由 Master 下发的规范化相对路径生成。

### 9.6 清理规则

- 只清理属于当前 `task_id + execution_id + node_id` 的临时文件；
- 绝不删除最终文件；
- 取消发生在 NAS 提交前：删除本执行临时文件；
- 取消发生在最终提交后：保留最终文件并上报事实；
- 过期 `.uploading` 文件需经现场表和 Master 租约共同确认后清理；
- 冲突文件保留最终文件和本地源文件，等待人工核验。

### 9.7 并发测试

至少测试：

- 20 个并发提交同一路径同一哈希，只有一个 Created，其余幂等；
- 两个并发提交同一路径不同哈希，最终文件保持一个完整版本，另一个冲突；
- 锁/原子 API 返回权限错误时不得继续 rename；
- Windows 本地 NTFS 测试；
- macOS 本地文件系统测试；
- Linux 本地文件系统测试；
- 真实 SMB/NAS 双机验收；
- 提交进程在拷贝、sync、rename 前后被强杀的恢复测试；
- 最终文件永远不出现部分内容。

## 10. R4：Worker 重启恢复状态机

### 10.1 禁止使用自由字符串裁决

在 protobuf 中定义技术枚举，避免空格、错别字和跨组件常量漂移：

```proto
enum ExecutionStage {
  EXECUTION_STAGE_UNSPECIFIED = 0;
  ACCEPTED = 1;
  SEARCHING = 2;
  DOWNLOADING = 3;
  LOCAL_FILE_READY = 4;
  NAS_UPLOADING = 5;
  NAS_COMMITTED = 6;
  RESULT_PENDING = 7;
}

enum ReconcileAction {
  RECONCILE_ACTION_UNSPECIFIED = 0;
  STOP_AND_RETRY = 1;
  RESUME_INGEST = 2;
  VERIFY_NAS = 3;
  REPLAY_RESULT = 4;
  CLEANUP_ONLY = 5;
}
```

这些名字是技术协议标识，可以使用英文；数据库、日志、UI 仍映射为中文：

| 技术枚举 | 中文展示值 |
| --- | --- |
| `ACCEPTED` | 已接受 |
| `SEARCHING` | 搜索中 |
| `DOWNLOADING` | 下载中 |
| `LOCAL_FILE_READY` | 本地文件完成 |
| `NAS_UPLOADING` | NAS 上传中 |
| `NAS_COMMITTED` | NAS 已原子落盘 |
| `RESULT_PENDING` | 结果待上报 |
| `STOP_AND_RETRY` | 停止并重试 |
| `RESUME_INGEST` | 继续入库 |
| `VERIFY_NAS` | 核验 NAS |
| `REPLAY_RESULT` | 重放结果 |
| `CLEANUP_ONLY` | 停止并清理 |

禁止再比较 `"NAS已原子落盘"` 之类字符串。

### 10.2 SQLite 现场字段

`execution_state` 至少保存：

- node_id；
- session_id；
- task_id；
- execution_id；
- stage；
- stage_version；
- task format；
- staging_dir；
- local_file_path；
- NAS relative path；
- source size；
- source SHA-256；
- result event_id；
- created_at、updated_at。

每次不可逆阶段变化必须先持久化并同步，再执行下一步。

### 10.3 上线与心跳上报

`NodeOnline.active_executions` 和 `Heartbeat.active_executions` 都必须使用同一个合并函数：

```text
SQLite 现场
  + 当前内存槽位现场
  → 按 execution_id 去重
  → 内存只补充更新字段，不删除 SQLite 记录
  → 上报 Master
```

在 Master 对账完成前：

- 不申请新会话；
- 不接收新任务；
- 继续发送合并后的心跳，维持仍有效现场的保护；
- 对账超时应断开重连，不得自行解除 `reconciling`。

### 10.4 Master 裁决表

Master 必须在事务或一致性快照中根据任务状态、租约、执行编号和阶段版本裁决：

| Worker 阶段 | 租约匹配 | Master 任务状态 | 裁决 |
| --- | --- | --- | --- |
| 已接受/搜索中/下载中 | 是 | 活动 | 停止并重试 |
| NAS 上传中 | 是 | 活动 | 清理本执行上传临时文件后重试 |
| 本地文件完成 | 是 | 活动 | 继续入库 |
| NAS 已原子落盘 | 是 | 活动或待确认 | 核验 NAS |
| 结果待上报 | 是或任务已完成 | 任意合法状态 | 重放结果 |
| 任意阶段 | 否 | 已被新执行领取 | 停止并清理，禁止提交 |
| 任意阶段 | 任意 | 已取消 | 停止并清理；最终文件不得删除 |
| 任意阶段 | 任意 | 已完成 | 重放尚未确认结果或清理现场 |

浏览器进程重启后不可恢复，因此搜索中、下载中不得返回“继续执行”。

### 10.5 Worker 裁决处理

每一种 `ReconcileAction` 必须有显式分支，默认未知值必须：

1. 记录协议错误；
2. 保持 `reconciling=true`；
3. 主动断链重连或停止 Agent；
4. 不得忽略后恢复新任务调度。

具体动作：

- `STOP_AND_RETRY`：取消内存执行、清理当前执行临时文件、通知 Master 释放旧执行；
- `RESUME_INGEST`：验证本地文件路径、大小和 SHA，继续 NAS 入库；
- `VERIFY_NAS`：读取最终相对路径并复算 NAS 文件证据，发送可靠核验事件；
- `REPLAY_RESULT`：只重放该 execution 对应的结果事件，不应笼统重放前 10 条；
- `CLEANUP_ONLY`：停止匹配执行、清理安全范围内临时文件、清除 SQLite 现场；
- 所有动作完成后发送逐执行 ACK；Master 收齐后再发送 reconciliation complete。

### 10.6 恢复测试矩阵

分别在以下时刻强杀 Worker 并重启：

1. 收到任务后；
2. 搜索中；
3. 下载中；
4. 本地文件校验完成后；
5. NAS 拷贝过程中；
6. NAS 原子落盘后、结果入 Outbox 前；
7. 结果入 Outbox 后、发送前；
8. Master 应用成功后、ACK 前；
9. Worker 收到 ACK 后、清理现场前。

每种场景验证：

- 最终只有一个 NAS 文件；
- 任务不会永久卡住；
- 额度不会重复扣减；
- 日统计不会重复增加；
- 执行记录不会永久运行中；
- 新执行不会被旧取消消息误伤；
- SQLite 现场最终被正确清理。

## 11. R5：结果、取消与重试的事务一致性

### 11.1 当前竞态

当前 `submit_result` 在事务外读取任务并判断 applicability，随后在新事务中仅按 `id` 更新。并发顺序可能是：

```text
结果线程读取：任务=执行中
管理员取消并提交：cancel_requested=true 或任务=已取消
结果线程无条件 UPDATE：任务=已完成/待处理/失败
```

这会复活已取消任务。

### 11.2 统一事务入口

结果处理必须：

1. 开启事务；
2. `SELECT ... FROM book_tasks WHERE id=$1 FOR UPDATE`；
3. 同一事务读取执行上下文；
4. 同一事务重新判断 execution_id、stage_version、task status、cancel_requested；
5. 决定 Apply、Backfill、AuditOnly 或 Conflict；
6. 使用带前置条件的 UPDATE；
7. 检查 `rows_affected == 1`；
8. 在同一事务更新文件、任务、执行记录、额度、统计和批次展示；
9. 提交后再发布 SSE 事件。

禁止在事务外做最终状态裁决。

### 11.3 成功结果 CAS 条件

示例条件必须至少包含：

```sql
UPDATE book_tasks
SET status = '已完成', ...
WHERE id = $1
  AND lease_execution_id = $2
  AND stage_version = $3
  AND cancel_requested = FALSE
  AND status IN ('已领取', '执行中', '待入库')
```

如果影响行数为零，重新读取任务并按当前事实处理，不能继续扣额度或增加统计。

### 11.4 失败结果 CAS 条件

失败、跳过和待确认更新也必须绑定：

- task id；
- lease execution id；
- stage version；
- 允许的活动状态；
- `cancel_requested=false`，除专用取消收尾路径外。

### 11.5 取消优先级与提交点

定义清晰的线性化语义：

- 任务行锁先被成功事务取得并提交：成功事实生效；后续批次取消只取消批次引用，不复写全局完成任务；
- 任务行锁先被取消事务取得并提交：旧结果不得复活任务；晚到文件证据只作审计或进入 NAS 待确认；
- 最终文件已经存在时绝不删除，即使取消先赢；
- 如产生未登记最终文件，创建严重告警并进入 NAS 核验，不得静默遗留。

### 11.6 批次状态迁移

取消批次前验证当前状态：

- 待开始、执行中、已暂停：允许取消；
- 已取消：幂等返回当前结果，不重复发送取消；
- 已完成：默认拒绝取消，除非另有明确“归档”功能；
- 不允许从已取消恢复到执行中；
- start、pause、resume、cancel 全部使用领域迁移校验。

### 11.7 精确取消

所有取消消息必须携带：

- node_id；
- session_id；
- task_id；
- execution_id；
- stage_version 或执行世代；
- 中文原因。

Worker 只取消全部字段匹配的当前执行。不得只按 task_id 或 session_id 取消，以免旧消息误伤新执行。

### 11.8 并发数据库测试

使用真实 PostgreSQL 和两个独立连接测试：

- 成功与批次取消同时提交；
- 失败与取消同时提交；
- 两个不同事件编号同时提交同一 execution 的成功；
- ACK 丢失后同一事件重放；
- 旧 execution 晚到、新 execution 已领取；
- 共享任务一个批次取消、另一个仍活动；
- 最后一个活动批次取消；
- 已完成批次取消被拒绝；
- 取消消息精确命中 execution；
- 每个场景验证任务、执行、文件、额度、日统计和批次展示六类数据。

## 12. R6：严格 NAS 证据闭环

### 12.1 字段语义

`book_tasks` 的证据字段必须有唯一明确来源：

| 字段 | 来源 |
| --- | --- |
| `expected_nas_relative_path` | Master 领取任务时生成的规范相对路径 |
| `expected_file_name` | 相对路径叶子文件名 |
| `expected_format` | 全局任务格式 |
| `expected_size_bytes` | Worker 最后一次可信文件证据 |
| `expected_sha256` | Worker 最后一次可信文件证据 |
| `evidence_execution_id` | 产生证据的执行编号 |
| `evidence_node_id` | 产生证据的节点编号 |
| `evidence_recorded_at` | Master 接收证据时间 |

### 12.2 写入时机

- 领取任务时写入路径、文件名和格式期望；
- Worker 在本地文件完成时上报大小与 SHA；
- Worker 在 NAS 原子落盘时再次上报最终大小与 SHA；
- 不确定结果进入“待确认”时，在同一事务固化全部已有证据；
- 后续核验不得用核验请求自身覆盖原期望证据；
- 证据变更必须记录操作日志和来源 execution。

### 12.3 核验请求

Master 只把已固化的期望字段发送给 Worker。若缺少关键字段：

- 缺路径：协议/数据错误，保持待确认并告警；
- 缺 SHA：允许检查文件是否存在，但不得自动判完成；
- 缺大小：允许计算实际大小，但不得把未知当匹配；
- 不得发送空字符串并让 Worker 解释为空表示跳过。

### 12.4 Worker 核验

Worker 必须：

1. 从本地 `nas_mount + expected_relative_path` 计算路径；
2. 执行 containment 校验；
3. 确认是普通文件；
4. 校验格式、魔数和大小；
5. 重新计算 SHA-256；
6. 返回实际相对路径、大小、SHA、节点和核验时间；
7. 不接受 Master 下发绝对路径；
8. 不修改或覆盖被核验文件。

### 12.5 Master 裁决

- 路径、格式、大小、SHA 全部一致：补登记文件并完成任务；
- 文件不存在：清理租约后回到待处理；
- 路径不一致：保持待确认并严重告警；
- SHA 不一致：保持待确认并严重告警，禁止重试覆盖；
- 文件过小或格式非法：保持待确认或进入失败，禁止登记为成功；
- 核验 execution/node 与期望来源不一致不一定失败，但必须审计实际核验节点。

### 12.6 测试

- 完整证据匹配；
- 缺 SHA 不得自动完成；
- 不同 SHA 保持待确认；
- 文件缺失回待处理；
- 路径逃逸请求被拒绝；
- 核验重复上报幂等；
- 两个 Worker 同时核验只完成一次；
- 旧核验结果不能覆盖新世代任务。

## 13. R7：管理员认证与会话安全

### 13.1 Cookie-only 会话

登录成功响应不得再返回 JWT。响应只返回用户公开信息：

```json
{
  "user": {
    "id": "...",
    "username": "admin",
    "role": "超级管理员",
    "status": "启用"
  }
}
```

Cookie 属性：

```text
Path=/
HttpOnly
Secure
SameSite=Lax 或 Strict
Max-Age=<服务端会话有效期>
```

建议 Cookie 名使用 ASCII，例如 `admin_session`，避免不同代理对非 ASCII Cookie 名处理不一致。

### 13.2 强制会话表验证

每个受保护请求必须：

1. JWT 签名、算法、exp、iat 校验通过；
2. `sub` 必须是合法 UUID；
3. `jti` 必须存在且是合法 UUID；
4. 查询 `admin_sessions.id=jti`；
5. session.user_id 必须等于 sub；
6. session 未撤销、未过期；
7. 对请求 token 计算 SHA-256；
8. 与 session.token_hash 常量时间比较；
9. 查询当前用户存在且状态启用；
10. 用户 token_version 等于 claims.ver；
11. 权限使用数据库当前 role，不信任 claims.role。

任意一步失败都返回 401，不允许非法 jti 返回 `None` 后继续认证。

### 13.3 登出与失效

- logout 无论 Cookie 是否过期都应返回清除 Cookie；
- token 可解析时撤销对应 session；
- 改密撤销该用户全部 session 并提升 token_version；
- 禁用用户撤销全部 session；
- 角色变化提升 token_version 并撤销全部旧 session；
- 删除用户依赖外键删除 session；
- 会话最后访问时间更新失败不应影响业务请求，但应限频更新并记录指标。

### 13.4 CSRF 和 CORS

- 生产管理前端采用同源部署；
- unsafe method 校验 `Origin` 或 Fetch Metadata；
- CORS 只允许显式配置的完整 Origin；
- `allow_credentials(true)` 时禁止通配符；
- 不信任客户端直接提供的 `X-Forwarded-For`；
- 仅信任来自 Caddy 内网地址的转发头；
- API 接收 JSON 的写请求必须要求正确 Content-Type；
- SSE 使用 Cookie 鉴权并校验用户实时有效状态。

### 13.5 登录限流

当前 HashMap 可被大量伪造 key 撑大。改为：

- IP 和规范化用户名双维度；
- 全局容量上限；
- 定期删除过期条目；
- 单 key 时间窗口和指数退避；
- 只使用可信代理链解析出的客户端 IP；
- 登录成功只清理对应用户名计数，不应让攻击者通过一次成功清空共享 IP 的所有防护；
- 达到阈值记录安全日志，但不得记录密码；
- 多 Master 实例时迁移到 Redis 或数据库，否则明确当前单实例限制。

### 13.6 密码和密钥

- JWT secret 至少 32 个随机字节，不接受示例弱密钥用于生产；
- 配置启动时识别示例密钥并拒绝；
- 密码继续使用 Argon2；
- 登录错误统一使用“用户名或密码错误”，避免枚举账户；
- API、日志和 panic 不返回密码哈希、JWT、session token；
- 发布前运行 Rust 与 npm 原生依赖审计。

### 13.7 认证测试

- Cookie 包含 Secure/HttpOnly/SameSite；
- JSON 不含 token；
- 空 jti、非法 jti、未知 jti 全部失败；
- token_hash 不匹配失败；
- session user 与 sub 不一致失败；
- 用户禁用立即失效；
- 改密立即失效；
- 角色修改旧会话失效；
- logout 清 Cookie；
- SSE 无认证失败；
- 只读用户所有写接口返回 403；
- 伪造 X-Forwarded-For 不能绕过限流；
- 大量随机用户名不会无限增长内存。

## 14. R8：本地 HTTP/CONNECT 代理

### 14.1 实现方向

优先使用成熟 HTTP 库处理 HTTP/1.1 framing，不再自行判断 chunked 结束标记。可采用 `hyper` / `hyper-util`：

- CONNECT：解析请求、注入上游 Proxy-Authorization、等待上游 200、升级为双向隧道；
- 普通 HTTP：由库解析请求体帧，删除客户端 Proxy-Authorization，注入当前会话上游凭据；
- 支持 Content-Length、chunked、无 body、HEAD、204、连接关闭定界；
- 限制请求头大小、单头数量、连接数和空闲时间；
- 上游凭据只存在内存，不输出日志。

若保留现有实现，必须正确处理：

1. 首次 header read 已经读入的 chunked body；
2. chunk terminator 跨 TCP 数据包；
3. trailer；
4. pipelined 下一请求数据；
5. response close-delimited body；
6. HEAD/1xx/204/304 无 body；
7. 不合法 Content-Length；
8. Transfer-Encoding 和 Content-Length 冲突；
9. 大小写和多值 Connection 头；
10. 上游半关闭和取消。

成熟库方案风险更低，推荐替换。

### 14.2 固定代理生命周期

- `LocalProxyServer` 属于一个槽位会话；
- CreateSession 时创建，EndSession 时关闭监听器和所有子连接；
- 同一会话期间上游 host/port/username/password 不可替换；
- 当前书失败不得在原会话静默换代理；
- 子连接任务必须由 cancellation token 统一回收；
- 关闭会话后旧连接不得继续使用 Webshare 凭据。

### 14.3 测试

- CONNECT 注入认证；
- HTTPS 隧道双向大数据；
- HTTP GET keep-alive；
- Content-Length POST；
- chunked body 与 header 同包；
- chunk terminator 跨包；
- chunked response；
- close-delimited response；
- 上游 407；
- 上游连接超时；
- 请求头超限；
- 客户端伪造 Proxy-Authorization 被替换；
- 会话关闭后所有连接退出；
- 日志不出现用户名密码组合。

## 15. R9：Webshare 完整快照同步

### 15.1 完整性原则

只有完整抓取成功的快照才允许影响“本次未出现代理”的状态。以下任一情况必须放弃整个同步，不修改数据库：

- 任一页网络错误；
- 非 2xx；
- JSON 解析失败；
- next URL 非官方 HTTPS；
- 发生重定向；
- 达到 MAX_PAGES 但仍有 next；
- 响应体超过上限；
- 出现重复冲突 external_id；
- 代理 host、port 或凭据结构非法。

当前“达到 50 页后 break 再同步”的行为必须改为返回错误。

### 15.2 HTTP 客户端安全

- 固定初始官方 API URL；
- 关闭自动重定向；
- 每一页 next 重新校验 scheme、host、port 和 path 前缀；
- 限制单页和总响应大小；
- 设置 connect、request、overall timeout；
- API Key 仅放 Authorization 头；
- 错误日志不得打印请求头；
- Webshare 错误响应正文截断并脱敏后记录。

### 15.3 数据校验

- host 非空且长度受限；
- port 在 1..=65535；
- username/password 长度受限；
- external_id 规范化且同一快照唯一；
- 同 external_id 若 host/port 改变，按 provider 身份更新，不应生成无法关联的重复记录；
- 密码缺失时只有明确语义才保留旧密码；
- 无效代理若已占用，标记 `retire_after_release=true`，不破坏当前书；
- 无效或消失代理不得再分配新会话。

### 15.4 同步事务

推荐使用同步世代：

1. 获取 Webshare 同步互斥锁；
2. 完整抓取并验证到内存；
3. 开事务；
4. 分配新的 `sync_generation`；
5. upsert 本次所有代理并标记 generation；
6. 只把旧 generation 且本次未出现的代理标记失效；
7. 已占用代理延迟退休；
8. 提交；
9. 发布一条汇总事件。

禁止两个定时同步任务同时执行。

### 15.5 测试

- 多页完整同步；
- 中间页失败数据库完全不变；
- 超页上限数据库完全不变；
- 恶意 next URL 被拒绝；
- 重定向被拒绝；
- 已消失未占用代理停用；
- 已消失占用代理延迟退休；
- 当前会话代理不会中途改变；
- 冷却到期但 provider 已失效的代理不得复活；
- 同 external_id 地址变化正确更新；
- 两次同步并发只有一个生效。

## 22. 实施 Agent 的工作规则

1. 开始前阅读 V3、V4、现有迁移和相关测试；
2. 不重写已经正确工作的领域模型；
3. 每次只完成一个 R 项并运行相关测试；
4. 修改 proto 后同步更新 Master、Worker 和协议测试；
5. 修改数据库必须新增迁移，不修改历史迁移；
6. 所有 SQL 使用参数化查询；
7. 所有外部输入在边界验证；
8. 所有凭据和令牌禁止日志输出；
9. 不通过扩大超时、忽略错误、删除断言来让测试变绿；
10. 遇到文件系统不支持安全语义时失败关闭，不实现危险 fallback；
11. 遇到无法执行的数据库、Windows、SMB 或 Docker 测试时明确报告“未验证”；
12. 完成后提交逐项对照表：问题编号、修改文件、测试名称、验收结果、剩余风险。

建议最终交付表格式：

| 问题编号 | 修改文件 | 新增/修改测试 | 结果 | 证据 |
| --- | --- | --- | --- | --- |
| V4-01 | ... | ... | 通过/未验证 | 命令输出或测试名 |

## 23. 明确禁止的错误修复方式

- 把 `require_client_cert` 默认改为 true，但 Worker 仍允许无证书连接；
- 把 Node CA 当作 Server CA；
- 通过关闭 TLS 校验解决 Caddy 内部 CA 问题；
- 忽略锁创建错误后继续 rename；
- 用更长 sleep 掩盖并发问题；
- 只在内存中修正状态，不持久化 SQLite；
- 对未知对账裁决使用 `_ => {}`；
- 用中文字符串替换另一个中文字符串，但仍让 Master/Worker各自维护常量；
- 在事务外判断状态后事务内无条件 UPDATE；
- 为通过测试而删除 `rows_affected` 检查；
- NAS 核验缺 SHA 时自动判成功；
- 登录响应继续返回 JWT，同时声称已经 Cookie-only；
- 超过 Webshare 页数上限后继续同步残缺快照；
- 数据库测试缺环境时打印“跳过”并返回成功；
- `npm test` 固定打印成功；
- 只运行构建、不运行真实集成测试就标记生产就绪。

## 24. 最终目标状态

修复完成后的关键闭环应当是：

```text
管理员创建批次并设置优先级
  → 全局图书/格式任务去重
  → Master 选择已审核 Worker 的可用槽位
  → 锁定站点账号 + Webshare 代理
  → Worker 通过 mTLS 长连接领取会话
  → 一本书全程固定同一代理/IP
  → 本地文件校验并持久化现场
  → NAS no-replace 原子提交
  → Worker 上报最终证据
  → Master 事务内 CAS 完成任务、文件、额度和统计
  → ACK 后 Worker 清理现场

任意位置断线或重启
  → SQLite + 内存现场合并上报
  → Master 按租约、世代和阶段裁决
  → 可证明的文件阶段继续入库/核验/重放
  → 不可恢复的浏览器阶段停止并安全重试
  → 不重复扣额度、不覆盖文件、不复活取消任务
```

达到这一状态后，系统才具备第一阶段约 5 台物理 Worker、约 5 个初始槽位规模的生产试运行条件。
