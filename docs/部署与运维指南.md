# 云端自动化平台部署与运维指南（V4）

> 对应《生产化修复实施方案-v4.md》第 4 节（信任边界）、第 8 节（TLS/mTLS）、
> 第 9 节（NAS no-replace）、第 16 节（部署与可观测性）、第 17 节（数据库运维）。

## 1. 推荐部署拓扑

```text
                公网（只开放 80/443）
                         │
                 ┌───────▼────────┐
                 │ Caddy（2 个域名）│
                 └───┬────────┬───┘
       admin.example.com   worker.example.com
       注册/API/静态站点      仅 OpenLink（mTLS）
                 │              │
                 ▼              ▼
            Master 8080    Master 9443（仅 Docker 内网）
                 │
                 ▼
      PostgreSQL 16 + OpenSearch（仅 Docker 内网）
```

- Master 与 PostgreSQL **只暴露到 Docker 内网**（docker-compose 用 `expose` 而非 `ports`）；
- OpenSearch 同样只开放到 Docker 内网，详细初始化和全量重建见
  [OpenSearch 接入与重建指南](./OpenSearch接入与重建指南.md)；
- 公网只开放 Caddy 的 80/443；
- 异地 Worker 通过 `worker.example.com` 的 mTLS 长连接接入；
- Worker 通过局域网直接把文件写到同一台 NAS（不经云端）。

## 2. 两种服务端证书部署方式

### 2.1 公网受信证书（推荐）

Caddy 自动申请 ACME 证书（Let's Encrypt）。Worker **不需要** `server_ca_file`
（系统根即可验证云端服务器）：

```toml
[master]
endpoint = "https://worker.example.com"
enroll_endpoint = "https://admin.example.com"
tls_domain = "worker.example.com"
identity_file = "data/identity.json"
client_cert_file = "data/client.crt"
client_key_file = "data/client.key"
node_ca_file = "data/node-ca.crt"
# server_ca_file 留空
```

### 2.2 私有 Server CA（`tls internal`）

Caddy 使用 `tls internal` 自签服务端证书，其内部 Server CA 根必须通过
**运维渠道**预先分发给每台 Worker：

1. 导出 Caddy 的 Server CA 根证书（`/data/caddy/pki/authorities/local/root.crt`）；
2. 核对 SHA-256 指纹：`openssl x509 -in root.crt -noout -fingerprint -sha256`；
3. 将根证书复制到 Worker 并配置为 `server_ca_file`；
4. **不能**通过未受信任的注册连接首次下载该根证书；
5. Node CA（`/app/data/ca.crt`，Master 首次启动自动生成）**只用于客户端证书**，
   绝不能加入 Worker 的服务端信任根。

```toml
[master]
endpoint = "https://worker.example.com"
enroll_endpoint = "https://admin.example.com"
tls_domain = "worker.example.com"
server_ca_file = "data/server-ca.crt"   # 管理员预先分发的 Server CA 根
```

Worker 配置了 `server_ca_file` 但文件缺失时，`worker-agent run` 会直接失败
（fail closed，第 8.3 节）。

## 3. 首次部署步骤

> **生产构建强制规则**：生产所用 Master 镜像必须由 GitHub Actions 的
> `deploy.yml` 构建并推送到 GHCR。生产服务器只负责拉取并运行已发布镜像，
> 禁止在生产机执行 `docker compose build`、`docker build`、`cargo build` 或
> 前端生产构建。Worker 同样只能使用 `release-worker.yml` 生成的 Release 包。

```bash
# 1. 准备 .env（参考 deploy/.env.example）
cp deploy/.env.example .env
# 编辑 .env：POSTGRES_PASSWORD / DATABASE_URL / MASTER_JWT_SECRET / MASTER_FIELD_KEY
#          / ADMIN_DOMAIN / WORKER_DOMAIN / MASTER_SITE_BASE
# 可选：CATALOG_MANIFEST_HOST_PATH（服务器书单只读目录）

# 2. 拉取 GitHub Actions 已发布到 GHCR 的镜像并启动
docker compose --env-file deploy/.env -f deploy/docker-compose.yml pull master
docker compose -f deploy/docker-compose.yml up -d
docker compose -f deploy/docker-compose.yml ps

# 3. 初始化管理员（容器内）
docker exec drission-master master-server --config /app/config/master.toml \
  create-admin --username admin --password '强密码'
```

> 注意：`config/master.example.toml` 里的是示例密钥。生产启动会拒绝示例弱
> JWT 密钥（第 13.6 节），必须用环境变量注入真实随机值：
> `openssl rand -base64 48` 生成 `MASTER_JWT_SECRET`，
> `docker compose exec master master-server keygen` 生成 `MASTER_FIELD_KEY`。

## 4. Worker 部署与自动注册 (V5)

已支持通过 GitHub Actions 自动构建跨平台 Releases（Windows、macOS ARM/Intel、Linux）。

详细使用与打包指南见：[Worker 跨平台客户端发布与使用指南](./Worker跨平台客户端发布与使用指南.md)。

```bash
# 1. 直接下载 GitHub Releases 对应平台的压缩包并解压
# 2. 修改 worker.toml 中的 nas_mount 挂载点与 endpoint
# 3. 双击启动（Windows 双击 .bat，macOS 双击 .command，Linux 运行 .sh）
#    首次启动 Worker 会自动发起直连登记，终端显示等待审核。
# 4. 管理员在 Web 控制台「节点管理」点击「批准接入」，Worker 自动下发 mTLS 证书并上线运行。
```

`run` 启动前强制校验（第 8.3 节）：endpoint 必须 HTTPS、身份/客户端证书/私钥
必须存在、证书与私钥匹配、证书未过期、私有 Server CA 配置存在、私钥权限 0600。

## 4.1 服务器书单 manifest

数据导入页除浏览器上传外，还可选择运维登记的服务器书单。生产 Compose 默认将
`CATALOG_MANIFEST_HOST_PATH` 挂载到 Master 的 `/app/catalog-manifests`，并设置
`DRISSION_CATALOG_MANIFEST_ROOT=/app/catalog-manifests`。

- 目录以只读方式挂载；
- 只列出目录第一层的 `.csv`、`.tsv`、`.txt` 文件；
- 单文件上限 8 MiB，最多展示 200 个文件；
- API 只接受列出的安全文件名，并在读取前进行规范路径与目录包含校验；
- 不要把 API Key、账号密码或其他密钥放入书单目录。

修改目录后重建 Master 容器即可生效：

```bash
CATALOG_MANIFEST_HOST_PATH=/srv/drission/manifests \
  docker compose -f deploy/docker-compose.yml up -d --force-recreate master
```

## 5. NAS 挂载与 no-replace 能力探测

- Worker 通过局域网挂载 NAS（SMB/NFS 均可），`nas_mount` 指向挂载点；
- Worker 启动时执行一次 no-replace 能力探测（第 9.3 节）：
  - Linux：`renameat2(..., RENAME_NOREPLACE)`；
  - macOS：`renamex_np(..., RENAME_EXCL)`；
  - Windows：`MoveFileExW`（不带 REPLACE_EXISTING）；
  - 均不支持时回退硬链接独占创建；仍不支持 → 节点进入「存储异常」，
    不再申请下载会话，管理平台产生严重告警；
- NAS 重新挂载（探针从不可用恢复）后自动重新探测；
- 探测结论与策略名会写进心跳的 NAS 状态明细，可在管理平台节点页查看。

跨平台路径约定：Master 只保存 NAS **相对路径**，Worker 负责拼接本地挂载点；
Windows 建议用 UNC 路径（`\\192.168.1.100\books`）避免盘符漂移。

## 6. 数据库备份、迁移与回滚

- 迁移由 Master 启动时自动执行（`auto_migrate = true`），文件内嵌在二进制中；
- **备份**（每日 + 变更前）：
  ```bash
  docker exec drission-postgres pg_dump -U postgres drission_book > backup_$(date +%F).sql
  ```
- **迁移回滚**：历史迁移（0001/0002）不可修改。若 0003 之后的迁移出现数据问题，
  用备份恢复数据库，同时回退 Master 二进制到对应版本；
- **迁移失败**：Master 的 `/health/ready` 返回 503，容器不进入健康状态，
  不会对外提供 API。

## 7. 健康检查与告警

- `/health/live`：进程存活（Docker HEALTHCHECK 用）；
- `/health/ready`：数据库可访问、迁移全部应用、关键配置有效；
- 健康接口不泄漏连接串、文件路径、证书内容或内部错误栈。

主要告警（管理平台「日志与告警」页可见）：

| 告警键 | 含义 |
| --- | --- |
| `NAS不可写:{node}` | NAS 挂载不可写 |
| `NAS空间:{node}` | NAS 剩余空间不足 |
| `NAS核验不一致:{task}` | 核验证据与期望不符（哈希/大小/路径/缺 SHA） |
| `Webshare同步失败` | Webshare 快照同步失败（数据库未改动） |
| `对账失败:{node}:{exec}` | Worker 无法执行对账裁决 |

## 8. 故障演练记录模板

每次演练记录：时间线、最终数据库状态、NAS 文件状态、告警。
见《实现进度.md》第 4 节的演练清单（第 16.4 节 10 项）。

## 9. 安全注意事项

- 代理密码、API Key、节点 token、JWT 绝不允许进入日志（代码层已约束）；
- Webshare API Key 为空时同步被明确禁用（第 16.1 节）；
- 会话 Cookie：`admin_session`，HttpOnly + Secure + SameSite=Lax；
- 登录失败统一返回「用户名或密码错误」，避免账户枚举；
- 只有来自 `trusted_proxies` 网段的 `X-Forwarded-For` 才被信任。

## 10. 版本发布前本地校验与发版规范（必须执行）

### 10.0 不可绕过的生产发布原则

1. 所有生产更新先形成 Git 提交并推送 GitHub；不得把生产服务器当作构建机。
2. Master 由 `deploy.yml` 在 GitHub 托管 Runner 中构建，推送 GHCR 后再部署。
3. Worker 由 `release-worker.yml` 构建跨平台安装包并发布到 GitHub Releases。
4. 生产机只允许执行备份、拉取已发布镜像、重建容器、健康检查和回滚。
5. 紧急修复也不得绕过流水线。GitHub Actions 失败或不可用时，应停止发布、
   保持现网版本并报告阻塞，不能改为 SSH 到生产机现场编译。
6. 发布成功必须记录：Git 提交、Actions 运行链接、镜像 SHA/Release 版本、
   数据库迁移结果、健康检查结果、回滚目标和发布后磁盘空间。

允许与禁止的操作边界：

| 场景 | 允许 | 禁止 |
| --- | --- | --- |
| Master 构建 | GitHub Actions `deploy.yml` | 生产机 `docker build` / `docker compose build` |
| Worker 打包 | GitHub Actions `release-worker.yml` | 本地或生产机临时编译后直接分发 |
| 生产部署 | 拉取 GHCR 镜像并重建 Master | 在生产目录修改源码后编译 |
| 紧急修复 | 提交、推送、等待流水线、验证 | 以“紧急”为由跳过 GitHub 打包 |

回滚时优先使用上一次已验证的 GHCR 镜像 SHA，而不是重新构建旧代码：

```bash
# 示例：将 compose 使用的镜像版本切到上一次已验证的 tag/SHA 后拉取并重建
docker compose --env-file deploy/.env -f deploy/docker-compose.yml pull master
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --no-deps master
docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps master
```

为确保推送到 GitHub 以及触发跨平台编译发布（GitHub Actions）100% 成功，所有版本升级或重大变更在 `git push` 前**必须在本地依次执行以下 5 步验证**：

```bash
# 1. 代码格式化与严格 Clippy 静态检查（零警告）
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings

# 2. 全工作区单元测试（覆盖 Master、Worker、Automation、Protocol 等全部模块）
cargo test --workspace --lib --bins

# 3. 前端自动化测试与生产编译
cd admin-web && npm test && npm run build && cd ..

# 4. 版本号一致性确认（发布新 Release 前）
#    确保以下两处版本号已同步修改：
#    - Cargo.toml (workspace.package.version)
#    - admin-web/package.json (version)

# 5. 确认当前 HEAD 提交即为待发布的最终提交
git log --oneline -3
```

### 10.1 两条发布流水线的触发规则

本仓库有两条相互独立的 CI/CD 流水线：

| 流水线 | 触发条件 | 作用 |
|--------|----------|------|
| `deploy.yml` (Build and Deploy) | `push` 到 `main`/`master` 分支 | 构建 Master Docker 镜像并自动部署到生产服务器 |
| `release-worker.yml` (Release Worker Binaries) | 推送 `v*` 格式的 tag | 交叉编译 Worker 四平台二进制并发布 GitHub Release |

**⚠️ 重要**：普通的 `git push` 只触发 Master 部署，**不会**触发 Worker 二进制打包。  
凡涉及 `crates/worker-agent/` 下代码的修改，**必须同时推送 tag** 才能让 Worker 用户获得新版本。

### 10.2 完整发版步骤（含 Worker 更新）

```bash
# 步骤 1-5：本地校验（见上方）

# 步骤 6：推送代码（触发 Master 部署）
git push origin main

# 步骤 7：打 tag 并推送（同时触发 Worker 跨平台编译与 GitHub Release 发布）
git tag vX.Y.Z
git push origin vX.Y.Z
```

> **注意**：tag 必须打在最终提交上（即 `git push` 之后再打 tag），否则 Release 中的 Worker 二进制与已部署的 Master 版本将不一致。

### 10.3 判断是否需要推送 tag

| 改动范围 | 是否需要推送 tag |
|----------|-----------------|
| 仅修改 Master 服务端代码 / 前端 / 文档 | 否，`git push origin main` 即可 |
| 修改了 `crates/worker-agent/` 下任意文件 | **是**，必须同时推送 `vX.Y.Z` tag |
| 修改了 `crates/platform-proto/` (gRPC 协议) | **是**，Worker 与 Master 协议需同步，务必打 tag |
| Cargo.toml workspace 版本号变更 | **是**，版本号变更应作为一次正式 Release |

推送 tag 后，在 GitHub → Actions → **Release Worker Binaries** 流水线查看构建进度（约 5~10 分钟），成功后即可在 GitHub Releases 页面下载对应平台的 Worker 安装包。
