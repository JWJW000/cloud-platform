# 云端自动化平台生产化修复实施方案

## 1. 文档用途

本文是交给后续实现 Agent 的执行说明，目标是把当前 `cloud-platform/` 从“领域模型与模拟联调骨架”修复为可以真实运行的第一版生产系统。

实现 Agent 应以本文作为任务清单和验收依据。不得仅以“能够编译”或“现有单元测试通过”作为完成标准；必须打通真实的 Master → Worker → 浏览器 → NAS → Master 闭环，并完成本文规定的集成与故障测试。

## 2. 当前结论

当前实现已经具备：

- 中文领域枚举与状态转换；
- PostgreSQL核心表结构；
- Master REST API、gRPC协议和调度模块骨架；
- Worker配置、心跳、槽位、outbox和NAS工具骨架；
- Webshare同步骨架；
- 基础管理后台；
- 134个单元测试。

但当前版本不能真实下载，主要阻断点包括：

1. Worker不处理`AssignTask`；
2. Worker始终使用`SimulatedEngine`；
3. 会话发送一次任务请求后直接退出；
4. NAS入库函数未接入执行链路；
5. 只申请0号槽位；
6. 槽位状态不能在会话结束后恢复；
7. Webshare本地转发没有代理认证且端口不一致；
8. 新节点连接后仍可能保持`离线`，无法被调度；
9. 当前任务租约不会随心跳/进度续期；
10. 断线现场、活动执行和outbox补报没有完整实现；
11. TLS/mTLS和Docker暴露方式不满足生产安全要求；
12. NAS核验与跨批次共享任务语义存在数据正确性问题。

## 3. 不可变业务约束

实现过程中必须遵守以下已确认规则：

1. Master部署在云端，通过Web管理后台操作。
2. 一台物理电脑定义为一个Worker。
3. 每台Worker由管理员分别配置最大浏览器槽位数。
4. 首期规模为5台Worker，每台约5个槽位，共约25个并发槽位。
5. Worker包含Windows、macOS、Linux。
6. 所有Worker位于同一局域网并访问同一台NAS。
7. 图书文件不经过云服务器。
8. 浏览器先下载到Worker本机临时目录，校验后再写NAS。
9. 公网断开时完成当前任务，不再领取新任务。
10. 一个账号的一轮会话固定使用一个Webshare代理。
11. 同一会话可连续下载多本书，直到额度耗尽、代理限流、会话异常或无任务。
12. 同一本书、同一格式全局只保存一份文件。
13. 多个批次只引用全局图书和全局任务。
14. 批次支持优先级、暂停、恢复和取消。
15. 数据库、REST JSON、gRPC业务载荷和前端中的业务枚举值使用中文。
16. UUID、时间戳、OS名、扩展名、MIME、协议名和代码标识保持标准技术值。

## 4. 完成定义

满足以下全部条件后，才可以把实现标记为完成：

1. `simulated=false`时真实启动Chromium并执行现有站点自动化。
2. 1台Worker配置5个槽位时，可以同时形成5个独立会话。
3. 每个会话绑定唯一账号和唯一Webshare代理，代理在会话内保持不变。
4. Worker能连续领取和执行多本书，而不是单任务后退出。
5. 下载文件经过本地暂存、NAS复制、目标哈希校验和原子提交。
6. Master只在NAS文件校验成功后把任务标记为`已完成`。
7. Worker与Master断网后完成当前任务并持久化结果，恢复后幂等补报。
8. 长时间下载期间任务租约持续续期，不会在正常执行时进入`待确认`。
9. Worker崩溃后，Master经过断线保护和NAS核验再决定是否重派。
10. Worker接入使用TLS和节点认证；生产端口不能绕过反向代理直接访问明文服务。
11. Docker部署缺少生产密钥时必须启动失败。
12. PostgreSQL集成测试、gRPC端到端测试、NAS测试和代理认证测试通过。

## 5. 修复优先级与阶段

必须按以下顺序实施，避免后续代码建立在错误的执行模型上：

1. 阶段A：建立可测试的运行时骨架；
2. 阶段B：打通Worker真实执行闭环；
3. 阶段C：修复多槽位和节点状态；
4. 阶段D：实现固定Webshare代理；
5. 阶段E：实现租约、断线恢复和outbox；
6. 阶段F：强化NAS一致性；
7. 阶段G：修复全局任务和批次语义；
8. 阶段H：完成TLS/mTLS和生产部署；
9. 阶段I：补齐集成、压力和故障测试；
10. 阶段J：单节点灰度，再扩至5台Worker。

## 6. 阶段A：重构Worker运行时骨架

### 6.1 目标

让槽位运行时独立于单次gRPC连接存在。gRPC断开和重连不能销毁Worker对当前会话和任务的认知。

### 6.2 当前问题

当前`SlotManager`在每次`connect_and_serve()`时重新创建。连接断开后，新连接无法知道旧会话；会话协程也不能把结束状态写回原管理器。

### 6.3 目标结构

建议引入长期存活的`WorkerRuntime`：

```rust
struct WorkerRuntime {
    identity: SavedIdentity,
    config: Arc<RwLock<EffectiveConfig>>,
    slots: Vec<Arc<SlotRuntime>>,
    outbox: LocalStore,
    link: Arc<LinkHandle>,
    storage: StorageManager,
}

struct SlotRuntime {
    index: u32,
    state: RwLock<SlotSnapshot>,
    command_tx: mpsc::Sender<SlotCommand>,
}
```

`WorkerRuntime`在`run_agent_loop()`外层创建一次，并跨重连复用。每个槽位拥有一个长期协程，通过`SlotCommand`接收：

- `创建会话`；
- `分配任务`；
- `取消任务`；
- `结束会话`；
- `暂停节点`；
- `恢复节点`；
- `关闭Agent`。

### 6.4 链路抽象

不能把具体的`mpsc::Sender`永久捕获在槽位协程里，因为重连后Sender会失效。建立可热切换的`LinkHandle`：

- 已连接时指向当前gRPC上行Sender；
- 断线时为`None`；
- 普通心跳和进度在断线时可以丢弃或聚合；
- 任务接受、任务结果、NAS核验、代理检测、会话结束必须先写outbox；
- 重连后flush outbox。

### 6.5 槽位状态必须由槽位协程自己维护

状态转换：

```text
空闲 → 已预留 → 启动中 → 执行中 → 收尾中 → 空闲
                         └→ 异常 → 收尾中 → 空闲
```

禁止由gRPC接收循环直接修改多个槽位字段。槽位协程结束时必须在`finally/guard`语义下：

1. 关闭浏览器；
2. 停止本地代理；
3. 清理或保留Profile；
4. 清除当前任务；
5. 清除当前会话；
6. 将槽位恢复为`空闲`或`异常`；
7. 上报最终槽位快照。

### 6.6 需要修改的文件

- `crates/worker-agent/src/client.rs`
- `crates/worker-agent/src/slot.rs`
- `crates/worker-agent/src/lib.rs`
- 可新增：
  - `crates/worker-agent/src/runtime.rs`
  - `crates/worker-agent/src/link.rs`
  - `crates/worker-agent/src/session.rs`

### 6.7 验收

- 模拟模式下创建5个槽位，能同时运行5个会话；
- 任一会话结束后对应槽位恢复`空闲`；
- gRPC断开并重连后，槽位和当前任务快照保持不变；
- 不再出现固定申请`slot_index=0`的逻辑。

## 7. 阶段B：打通真实任务执行闭环

### 7.1 Master与Worker消息流程

```text
Worker空闲槽位
  → SessionRequest
Master原子锁定槽位、账号、代理
  → CreateSession
Worker启动固定代理、Profile和浏览器并登录
  → SessionReady（需要新增或复用明确消息）
Master把会话改为运行中
Worker请求下一本
  → NextTaskRequest
Master领取全局任务
  → AssignTask
Worker先持久化接受事件
  → TaskAccepted
Worker执行搜索与下载
  → TaskProgress
Worker把本机文件入库NAS
  → TaskResult（带FileEvidence）
Master幂等提交结果
Worker继续请求下一本
```

### 7.2 必须处理全部关键下行消息

`handle_master_message()`至少完整处理：

- `NodeConfig`：校验并应用配置版本；
- `CreateSession`：发送给指定槽位；
- `AssignTask`：发送给对应会话所在槽位；
- `NoTaskAvailable`：会话按重试时间等待，不立即退出；
- `PauseNode`：完成当前任务后停止领取；
- `ResumeNode`：恢复领取；
- `EndSession`：按`finish_current_task`收尾；
- `CancelTask`：在安全检查点取消；
- `VerifyNasFile`：实际检查NAS并上报；
- `RefreshConfig`：请求或等待完整配置；
- `PrepareUpgrade`：若首期不实现自动升级，必须明确回报“不支持”，不能静默忽略。

### 7.3 引擎工厂

配置必须真正生效：

```rust
enum EngineMode {
    Real,
    Simulated,
}

fn build_engine(config: &EffectiveConfig) -> Arc<dyn AutomationEngine>
```

- `simulated=true`使用`SimulatedEngine`；
- `simulated=false`使用真实`RealAutomationEngine`；
- 不允许生产配置静默回退到模拟引擎；
- Master和管理后台应显示Worker当前引擎模式。

### 7.4 真实自动化引擎

新增`RealAutomationEngine`，复用根项目已有逻辑：

- `src/browser/worker.rs`中的登录、搜索、匹配、下载和配额判断；
- `src/browser/detector.rs`中的浏览器探测；
- `src/mail.rs`中的验证码接口；
- `src/domain.rs`中的文件名匹配；
- 现有站点故障、未收录、相似书、隐藏卡片和下载文件错配规则。

不要让`automation-core`依赖原SQLite Store。需要把现有自动化逻辑改造成由输入参数驱动、以结构化结果返回的站点驱动层。

`RealAutomationEngine`必须实现：

- `open_session()`：启动浏览器、使用会话Profile和固定代理、登录账号；
- `download_book()`：按书名搜索、ISBN辅助匹配、下载到任务暂存目录；
- `read_quota_indicator()`；
- `register_account()`；
- `close_session()`。

### 7.5 任务执行

收到`AssignTask`后：

1. 核对`session_id`与本槽位当前会话一致；
2. 核对当前槽位没有另一个任务；
3. 将`TaskAccepted`写入outbox；
4. 上报`TaskAccepted`；
5. 创建`staging/task-{task_id}`；
6. 调用`download_book()`；
7. 消费并节流`AutomationEvent`；
8. 成功后调用NAS入库；
9. 生成稳定的`TaskResult event_id`并先写outbox；
10. 上报结果；
11. 清除当前任务；
12. 若会话仍可运行，则请求下一本。

任务结果事件重发时必须复用相同`event_id`，不能每次重连生成新编号。

### 7.6 需要修改的文件

- `crates/automation-core/src/engine.rs`
- `crates/automation-core/src/types.rs`
- 新增`crates/automation-core/src/real.rs`
- `crates/automation-core/Cargo.toml`
- `crates/worker-agent/src/client.rs`
- `crates/worker-agent/src/slot.rs`
- `crates/worker-agent/src/storage.rs`

### 7.7 验收

- 模拟模式完成完整任务和NAS入库；
- 真实模式能启动Chromium而不是模拟引擎；
- 真实模式至少完成一次搜索到本机暂存的冒烟测试；
- `AssignTask`不再进入通配忽略分支；
- 一个会话连续完成至少2个任务；
-所有状态和阶段上报为中文。

## 8. 阶段C：节点状态与多槽位

### 8.1 节点上线规则

审核通过后的节点初始状态可以是`离线`，但合法节点建立gRPC连接并完成首个健康心跳后，Master必须按以下规则更新状态：

```text
管理员状态为已禁用/维护中/已暂停 → 保持管理员状态
NAS不可用                         → 存储异常
NAS正常且有空闲槽位               → 在线
NAS正常且无空闲槽位               → 忙碌
连接断开且超过离线阈值             → 离线
```

不要把`connected`布尔值与业务状态混为一谈，但两者必须保持一致。

### 8.2 Worker配置来源

- 注册时`requested_slots`只是申请值；
- 管理员批准后的`NodeConfig.max_slots`才是权威上限；
- Worker必须动态应用`NodeConfig`；
- 缩容时已运行槽位完成当前任务后停用；
- 扩容时创建新的槽位协程；
- Worker不得超过Master批准的上限。

### 8.3 会话激活

当前Master的`scheduler::activate()`没有调用者。新增明确的`SessionReady`消息，Worker在以下条件全部满足后发送：

- 本地代理已启动；
- 出口IP检测成功；
- Chromium已启动；
- 账号已登录；
- Profile已就绪。

Master收到后才把会话从`创建中`改为`运行中`。

### 8.4 非法状态处理

禁止以下默认行为：

- 非法槽位状态默认成`空闲`；
- 非法任务类型默认成`图书下载`；
- 非法执行结果默认成`可重试失败`。

非法业务值必须拒绝、记录告警并返回明确错误，不能静默改变资源状态。

### 8.5 验收

- 新节点审核后连接并健康上报，自动进入`在线`；
- NAS异常自动进入`存储异常`，恢复后自动回`在线/忙碌`；
- 5槽位可同时创建5个会话；
- 管理员将5槽位调整为3槽位时不强杀当前任务；
- 非法状态上报不会把已占用槽位释放为空闲。

## 9. 阶段D：固定Webshare代理

### 9.1 必须修复的问题

当前`LocalProxyServer`只做TCP透传，没有注入上游认证；同时实际监听端口与传给Chromium的端口可能不一致。

### 9.2 推荐实现

优先选择一种并完整实现，不要保留两个未完成路径：

#### 方案一：Worker托管gost子进程

- 每个会话生成独立临时gost配置；
- 本地监听`127.0.0.1:{CreateSession.local_forward_port}`；
- 配置中固定唯一Webshare上游及认证；
- 会话结束时停止对应子进程并删除临时配置；
- 子进程异常退出时结束会话并把代理标为`异常`。

#### 方案二：Rust内建认证代理

- 正确解析HTTP代理请求和CONNECT；
- 向上游注入Basic Proxy Authorization；
- 支持配置声明的`http`/`https`/`socks5`；
- 不记录认证头；
- 正确处理半关闭、超时和取消；
- 编写代理协议集成测试。

若选择方案二，不得继续把未解析的浏览器字节原样转发后声称已完成认证注入。

### 9.3 端口规则

- 唯一权威值为`CreateSession.local_forward_port`；
- 监听端口、Chromium参数和日志必须使用同一个值；
- 删除Worker端`18000 + slot_index`等重复推导；
- 端口被占用时会话创建失败，不得自动切换到Master不知道的新端口。

### 9.4 出口IP验证

会话准备阶段通过本地代理查询出口IP：

- 记录`proxy_id + session_id + exit_ip`；
- 会话中不得切换上游；
- 代理连接失败时不消耗图书重试次数；
- 账号未满但站点限流时代理进入`冷却中`，账号保持`已注册`；
- 账号显示额度已满时账号进入`今日额度耗尽`，代理不受处罚。

### 9.5 Webshare同步

- `valid=false`的代理不得进入`可用`；
- 同步后不再存在于Webshare列表的代理应标记`已停用`，但正在租用的代理应在会话结束后再停用；
- 首次启动应立即同步一次，之后按周期同步；
- API失败不得清空现有代理池；
- 分页URL必须只接受可信Webshare域名，避免异常响应引导访问任意地址。

### 9.6 验收

- 使用需要用户名密码的测试上游代理，通过本地端口访问成功；
- 上游能确认认证头正确；
- 浏览器实际出口IP与Master分配代理一致；
- 同一会话连续下载时出口IP保持不变；
- 5个槽位使用5个独立端口和5个独立上游；
- `valid=false`代理不会被调度。

## 10. 阶段E：任务租约、断线恢复与Outbox

### 10.1 任务续租

当前心跳只续租会话。必须让心跳中的`active_executions`携带：

- `session_id`；
- `execution_id`；
- `task_id`；
- 当前中文任务状态；
- `stage_version`。

Master在同一处理流程中条件续租任务：

```sql
UPDATE book_tasks
SET lease_expires_at = now() + interval '... seconds'
WHERE id = :task_id
  AND lease_session_id = :session_id
  AND lease_execution_id = :execution_id
  AND stage_version = :stage_version
  AND status IN ('已分配', '执行中', '等待入库');
```

进度上报成功时也可顺带续租，作为心跳之外的第二保障。

### 10.2 Worker本地执行现场

本地SQLite增加：

- `active_sessions`；
- `active_executions`；
- `pending_files`；
- `outbox`；
- `applied_config`。

关键状态变化应使用本地事务写入。Worker进程重启后先读取现场，再连接Master对账。

### 10.3 Outbox规则

以下事件必须先落盘，再尝试发送：

- `TaskAccepted`；
- `TaskResult`；
- `NasCheckResult`；
- `ProxyCheckResult`；
- `SessionReady`；
- `SessionClosed`；
- 影响Master事实状态的其他事件。

规则：

1. 同一业务结果只有一个稳定`event_id`；
2. 发送失败保留；
3. 收到`EventAck.accepted=true`才删除；
4. 重放时只设置`replayed=true`，不改事件编号和业务载荷；
5. 需要补报的事件不能因队列满而丢弃；
6. outbox应启用WAL和合理的busy timeout；
7. outbox文件及身份文件权限应限制为当前服务账户可读。

### 10.4 断网行为

连接断开时：

- 当前已接受任务继续；
- 不发送新的`NextTaskRequest`；
- 不创建新会话；
- 当前任务完成后写NAS；
- 结果写outbox；
- 当前会话进入本地“等待重连”；
- 网络恢复后先发送`NodeOnline.active_executions`和outbox，再申请新任务。

### 10.5 Master重连对账

Master不能只统计`active_executions.len()`。必须逐条对账：

- 执行编号仍与租约一致：恢复会话和任务租约；
- Master已提交成功：通知Worker清理本地现场；
- Master已回收但Worker有文件结果：允许带可靠文件证据的幂等回填；
- 执行编号未知：只留审计，不覆盖当前任务；
- 同一节点旧连接的清理不能注销新连接。

### 10.6 断线保护

- 心跳间隔默认15秒；
- 连续错过3次后节点`离线`；
- 断线保护默认15分钟；
- 保护期内不重新分配当前任务、账号和代理；
- 保护到期后先把可能已开始的任务置`待确认`；
- 由其他在线Worker执行NAS核验；
- 确认文件不存在后才重新进入`待处理`。

### 10.7 验收

- 模拟一个执行时间超过5分钟的任务，租约不超时；
- 下载中切断Master网络，Worker完成任务并写outbox；
- 恢复网络后任务只完成一次、账号额度只增加一次；
- Worker进程在任务中途崩溃，重启后能恢复或正确对账；
- 重复发送相同事件不会重复累计统计；
- 两个不同事件编号重复提交同一执行结果，也不能重复消耗账号额度。

## 11. 阶段F：NAS一致性与安全

### 11.1 入库流程

必须执行：

```text
本机下载完成
  → 检查浏览器临时扩展名消失
  → 校验书名、格式、大小
  → 计算本机SHA-256
  → 复制到NAS唯一临时文件
  → 刷新并关闭目标文件
  → 重新读取NAS临时文件并计算SHA-256
  → 比较源/目标大小和哈希
  → 目标最终文件不存在时原子重命名
  → 最终文件已存在时先核验，禁止盲目覆盖
  → 生成FileEvidence
  → 删除本机临时文件
```

### 11.2 路径安全

- Master下发的是相对路径；
- Worker拒绝绝对路径；
- Worker拒绝`..`、根目录前缀和平台盘符逃逸；
- 规范化后目标必须仍位于`nas_mount`下；
- 最终文件名经过跨平台非法字符清理；
- Windows保留名和尾随点/空格必须处理。

### 11.3 并发与重复文件

- NAS临时文件名包含任务、执行和节点编号；
- 不同Worker不得共用固定健康探针文件名；
- 健康探针使用节点编号和随机后缀；
- 最终文件已存在且哈希一致：视为幂等成功；
- 最终文件已存在但哈希不同：任务进入`待确认`并告警，禁止覆盖。

### 11.4 NAS核验

Master下发核验命令时应包含：

- 任务编号；
- 预期NAS相对路径；
- 预期格式；
- 已知大小；
- 已知SHA-256（存在时）。

Worker上报后，Master至少验证：

- 上报路径与任务路径一致；
- 格式与任务格式一致；
- 文件名与预期一致；
- 大小大于最低阈值；
- SHA-256非空；
- 有已知哈希时必须一致。

不满足时不得登记`book_files`，任务保持`待确认`并产生告警。

### 11.5 空间检测

- 删除`staging_free_gb=100`硬编码；
- 真实检测本机暂存卷剩余空间；
- 无法识别NAS挂载卷时返回“未知”，不得伪造100GB；
- “未知”与0GB必须区分；
- 低于阈值停止领取新任务，但允许当前文件完成入库。

### 11.6 验收

- NAS复制后篡改一个字节，入库必须失败；
- 两台Worker同时提交同一文件，不覆盖有效正本；
- Windows、macOS、Linux路径测试通过；
- `../outside.pdf`被拒绝；
- 核验上报其他文件路径不能把任务标成完成；
- NAS中断后任务进入`等待入库`，恢复后继续。

## 12. 阶段G：全局图书、批次和任务语义

### 12.1 批次取消

取消批次只取消该批次的需求，不应直接破坏仍被其他有效批次引用的全局任务。

有效引用包括：

- `待开始`；
- `执行中`；
- `已暂停`。

只有当一本书不再被任何有效批次引用时，才允许取消尚未终态的全局任务。若任务正在执行：

- 还有其他有效批次引用：继续执行；
- 没有其他有效批次引用：设置取消请求并通知Worker完成安全收尾。

### 12.2 批次显示状态

`batch_books.display_status`不能简单永久复制全局任务状态而失去批次语义。例如批次A取消后，该关联在批次A中应显示`已取消`，但共享全局任务可继续为批次B执行。

建议新增或明确：

- `batch_books.request_status`：`有效`/`已取消`；
- 展示状态根据请求状态、全局任务和文件状态计算；
- 取消一个批次只改变该批次关联状态。

### 12.3 图书合并

合并必须在单事务内处理：

1. 锁定源图书和目标图书；
2. 处理同批次重复关联；
3. 把源批次关联迁移到目标；
4. 合并或裁决源/目标任务；
5. 合并或裁决源/目标文件；
6. 有正在执行任务时禁止合并或先安全结束；
7. 删除重复关联而不是留下指向已合并图书的孤立行；
8. 最后标记源图书`已合并`。

如果源和目标各有不同有效文件，必须进入人工裁决，不能静默覆盖。

### 12.4 结果并发幂等

当前“检查适用性”和“提交成功”需要放入同一数据库事务，并锁定任务/执行记录。即使Worker错误地产生两个不同`event_id`的同一结果，也只能：

- 登记一份文件；
- 消耗一次账号额度；
- 增加一次每日成功统计；
- 增加一次会话完成计数。

成功更新应带条件：

```sql
WHERE id = :task_id
  AND lease_execution_id = :execution_id
  AND stage_version = :stage_version
  AND status IN ('已分配', '执行中', '等待入库')
```

若影响行数为0，只留审计，不做任何计数。

### 12.5 验收

- 相同图书属于执行中批次和暂停批次时，取消其中一个不取消全局任务；
- 所有批次取消后，全局待处理任务才取消；
- 两批次共享一本书，只产生一份NAS文件；
- 并发提交两个成功事件，账号额度和每日统计只增加一次；
- 合并两本已有任务的图书不会留下永远无法收尾的批次。

## 13. 阶段H：TLS、mTLS和部署安全

### 13.1 节点注册与证书

Worker执行`enroll`时：

1. 本地生成私钥；
2. 生成包含节点标识的CSR；
3. 使用一次性注册码调用`Enroll`；
4. 保存节点编号、token、客户端证书、客户端私钥和Master CA；
5. 私钥和token文件权限限制为服务账户可读；
6. 后续`OpenLink`加载客户端Identity和CA证书；
7. 不得在日志中打印注册码、token、证书私钥或账号/代理密码。

当前Worker日志会打印注册码，应删除。

### 13.2 TLS终止

可保留Caddy终止TLS，但必须满足：

- Caddy使用正式域名证书；
- Caddy能够读取Master节点CA证书；
- Caddy的客户端证书模式至少请求证书；
- `OpenLink`必须由应用层强制验证透传指纹；
- Caddy必须覆盖并清除来自公网客户端伪造的指纹头；
- Master只信任来自Caddy内部网络的指纹头；
- 生产配置`require_client_cert=true`。

也可以让Tonic直接终止mTLS，但Enrollment与OpenLink的证书要求必须分别设计清楚。

### 13.3 Docker网络

- PostgreSQL不暴露公网；
- Master的8080和9443只使用Docker内部`expose`，不绑定宿主公网；
- 只有Caddy暴露80/443；
- 80只做HTTPS重定向；
- gRPC和Web API统一走443；
- 防火墙只开放必要端口。

### 13.4 密钥

以下值生产环境必须显式提供，缺失时Master拒绝启动：

- PostgreSQL密码；
- JWT签名密钥；
- AES字段加密密钥；
- Webshare API Key（启用同步时）；
- CA私钥或其持久化位置。

删除Docker Compose中的公开默认值。提供`.env.example`但只放占位符，不放可运行密钥。

### 13.5 JWT与用户状态

JWT提取器至少应处理用户被禁用或角色变更：

- 每次敏感写操作回查当前用户状态和角色；或
- 使用短期JWT加用户`token_version`；
- 修改密码、禁用用户时使旧token失效；
- `logout`如保持无状态，应在文档中明确只清理客户端token。

### 13.6 验收

- 未带节点证书的`OpenLink`被拒绝；
- 被撤销证书被拒绝；
- 伪造指纹头不能绕过mTLS；
- 宿主机无法直接从公网访问8080/9443；
- 缺少JWT或字段密钥时容器启动失败；
- Worker能够使用保存的CA验证服务端；
- 日志中搜索不到注册码、token、账号密码和代理密码。
