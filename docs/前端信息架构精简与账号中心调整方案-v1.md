# 前端信息架构精简与账号中心调整方案 V1

> 状态：待实施
> 日期：2026-08-25
> 适用目录：`cloud-platform/admin-web`
> 前置设计：`docs/图书馆总库与索引设计方案-v1.md`

## 1. 方案目标

当前总库方案已经实现后，前端同时保留了新总库页面和旧批次页面，导致同一业务出现多个入口：

- “总览”与“总库概览”同时存在；
- “总库检索”与“历史图书”同时存在；
- “全局获取池”“下载批次”“历史任务”同时存在；
- “导入中心”与“上传 CSV 建批”同时存在；
- “下载账号”“账号注册批次”“统一任务中的账号注册”同时存在。

本次调整要实现：

1. 图书下载始终只有一个持续运行的全局获取池。
2. 账户注册能力完整保留，并收敛到一个清晰的“账号中心”。
3. 导入批次只表示数据出处和导入历史，不再表示独立下载任务。
4. 一级导航从当前 18 项缩减为 8 项。
5. 删除已经被新总库模型替代的旧页面，不让用户选择“新旧两套事实”。
6. 运维功能继续保留，但从业务主导航降级到运行资源或系统管理。
7. 所有页面按用户理解的对象命名，不在主要界面暴露 UUID、内部表名、SSE、Outbox 等实现细节。
8. 调整期间不删除 PostgreSQL 历史数据，不立即移除旧 HTTP 端点。
9. 将旧单机程序的 `outlook-mail` 自动取码能力迁移到云端 Worker，支持运行时切换 Provider，自动取码失败时自动降级到人工验证。

## 2. 产品定位与设计原则

### 2.1 产品定位

- **产品主题**：面向内部管理员的数字图书馆总库与分布式获取平台。
- **主要用户**：书目管理员、下载任务管理员、系统管理员和只读审计人员。
- **页面的单一核心工作**：让管理员随时知道总库还缺什么、系统正在做什么、下一件需要人工处理的事是什么。

账户注册是下载所需的资源准备工作，不是第二条图书业务主线。它必须完整、易找，但不能与图书获取任务混在同一个任务列表中。

### 2.2 信息架构原则

1. **按用户对象组织**：图书、获取任务、导入、账号、Worker、待处理事项。
2. **一个对象一个权威入口**：同一数据不能同时由“新页面”和“历史页面”管理。
3. **业务状态优先**：默认显示待处理、运行中和异常；已完成历史作为筛选项或详情信息。
4. **技术细节按需展开**：SHA-256、原始 JSON、UUID、代理租约放入“技术详情”。
5. **查询状态可复现**：搜索词、筛选、标签页和游标写入 URL。
6. **删除浅页面，保留深模块**：页面不只是把后端表格原样透传；一个页面模块应隐藏分页、错误处理、权限和操作状态。

最终只保留以下 8 个一级入口：

| 3 | 获取任务 | `/acquisitions` | 唯一全局获取池中的待下载、运行、失败和确认任务 |

## 6. 页面完整调整

### 6.1 总览

#### 页面目标

回答四个问题：总库有多少、已补齐多少、当前是否正常、现在最需要处理什么。

#### 保留内容

- 规范作品数、版本数和来源记录数；
- 已下载、待下载、运行中、失败、待确认；
- 已校验馆藏文件与存储量；
- 在线 Worker 与可用槽位；
- 可用账号、今日额度耗尽账号；
- 最近一次导入；
- 待处理事项总数。

#### 删除或收起

- 删除“运行总览”和“总库概览”两套卡片；
- 删除最近执行的大表格，只保留最近异常 5 条；
- 删除无法点击下钻的装饰性统计；
- SSE 正常状态不常驻显示，只有重连或断开时出现提示。

#### 页面结构

```text
┌──────────────────────────────────────────────────────────────┐
│ 总库补齐进度：书目 → 来源 → 排队 → 下载 → 校验 → 馆藏       │
└──────────────────────────────────────────────────────────────┘
┌─────────────┬─────────────┬─────────────┬─────────────┐
│ 总库版本     │ 已下载       │ 待下载       │ 需要处理     │
└─────────────┴─────────────┴─────────────┴─────────────┘
┌────────────────────────────┬─────────────────────────────┐
│ 运行状态：Worker / 账号     │ 最近导入与异常              │
└────────────────────────────┴─────────────────────────────┘
```

“总库补齐进度轨”是整个产品的视觉签名。它表达真实业务阶段，不作为纯装饰动画。

### 6.2 图书总库

#### 页面目标

快速找到一本书，并明确它的规范版本、来源候选和馆藏状态。

#### 列表保留

- 标题、作者；
- 出版社和年份；
- ISBN/DOI 中最重要的一个；
- 语言和作品类型；
- 来源格式；
- 馆藏格式；
- 获取状态。

#### 调整

- 使用游标分页：`cursor`、`next_cursor`、`previous_cursor`；
- 删除“第 N / 总页数”深分页；
- 搜索、语言、格式、作品类型、获取状态全部写入 URL；
- 默认折叠低频筛选，避免左侧过滤器过长；
- 结果行点击标题进入详情，行内只保留一个主要动作；
- “已下载”仍可筛选，但不能在获取任务页重复展示全部完成历史。

#### 详情页调整

标签名称简化为：

1. 来源；
2. 候选文件；
3. 馆藏；
4. 执行记录。

默认展示普通管理员能理解的内容。以下信息放入“技术详情”：

- 作品/版本/来源 UUID；
- 完整原始 JSON；
- 文件完整 SHA-256；
- 租约、执行事件和内部阶段版本。

### 6.3 获取任务

#### 页面目标

管理唯一全局获取池中的可行动任务。

#### 默认状态

- 待下载；
- 排队中；
- 下载/校验中；
- 暂时失败；
- 人工确认。

#### 删除

- 删除“已下载”快捷标签；
- 删除与图书总库完全相同的通用搜索结果展示；
- 删除旧批次名称作为主分组；
- 删除账号注册任务混排。

#### 保留与新增

- 书名、目标版本、候选格式；
- 当前状态与阶段；
- 优先级、尝试次数、下次重试时间；
- 当前 Worker/槽位；
- 最近失败原因；
- 重试、暂停、恢复、改优先级和进入人工确认；
- 原始书单/导入来源仅作为筛选条件。

大规模批量操作必须先显示影响数量，再二次确认。

### 6.4 数据导入

#### 页面目标

让管理员知道数据来自哪里、导入到哪里、是否有丢行或隔离数据。

#### 路由标签

- `/imports`：导入运行；
- `/imports?tab=sources`：数据源；
- `/imports?tab=quarantine`：隔离数据；
- `/imports?tab=legacy`：旧批次只读兼容。

#### 导入入口

保留两种入口：

1. **上传补充书单**：适合较小 CSV/XLSX；
2. **启动服务器目录导入**：选择已登记的数据源清单或目录 manifest，适合移动硬盘和对象存储。

删除当前以“来源名称 + 文件名 + 粘贴大量 CSV 文本”为主要流程的弹窗。少量粘贴录入可以放在“快速新增”次要操作中，限制行数并明确用途。

#### 隔离数据

- 列表采用分页，不一次渲染全部卡片；
- 支持按错误原因和来源筛选；
- 修复时展示字段映射，不只允许补书名；
- 修复后显示重新解析结果；
- 待处理中心只展示隔离数量与链接，不复制整套列表。

### 6.5 账号中心

账户注册功能在本方案中完整保留，并提升为独立一级入口。

#### 账号中心首页 `/accounts`

顶部摘要：

- 可用账号；
- 待注册；
- 注册中；
- 待人工验证；
- 今日额度耗尽；
- 已禁用/异常。

账号表格：

- 邮箱与昵称；
- 注册状态；
- 下载可用状态；
- 今日用量/额度；
- 最近登录和最近错误；
- 启用、禁用、重新注册、查看详情。

#### 注册队列 `/accounts/registrations`

状态：

- 待注册；
- 已分配；
- 注册中；
- 等待验证码；
- 正在重试；
- 已完成；
- 失败；
- 已取消。

操作：

- 启动/暂停注册队列；
- 单项重试或取消；
- 批量重试失败项；
- 调整优先级；
- 查看 Worker、执行阶段和失败原因；
- 跳转到待人工验证。

#### 批量导入账号

继续支持：

- `email----password` 文本；
- CSV；
- 导入为“待注册”；
- 导入为“已注册”；
- 文件内重复、库内重复和错误行预检；
- 敏感字段不进入日志和预览响应。

流程简化为：

```text
选择文件 → 选择账号状态 → 预检 → 确认导入
                                  └→ 待注册账号自动进入注册队列
```

删除“导入后再询问是否创建注册批次”的额外概念。管理员选择“待注册”就表示这些账号应进入注册队列；是否立即启动只保留一个明确开关。

#### 注册分组

后端批次继续存在时，前端名称统一为“导入分组”或“注册分组”，只用于：

- 追溯一次导入；
- 批量暂停/恢复；
- 查看该组成功率；
- 导出失败记录。

它不是一级导航，也不是第二套任务中心。

#### Outlook 自动取码与人工降级

`outlook-mail` 是账户注册链中的邮件验证码 Provider，不是独立业务系统。旧单机程序中已有 `MailClient` 抽象、`OutlookEmailClient` 和提交注册前记录旧验证码的逻辑。迁移时保留这些已验证行为，不直接复制同步 HTTP 实现。

自动注册流程：

```text
开始注册
  → Provider 记录该邮箱当前邮件游标
  → Worker 提交站点注册表单
  → 检测到邮箱验证码输入框
  → Provider 只等待游标之后的新验证码
  → Worker 填写并提交验证码
  → 成功：账号进入可下载状态
  └→ 超时/不可用/解析失败：生成一条人工验证事项
```

注册队列增加可见阶段：

- 等待邮件；
- 自动取码中；
- 提交验证码；
- 等待人工验证；
- Provider 暂时不可用。

每个任务显示验证方式“Outlook 自动”或“人工”，但不显示验证码、邮件正文、API Key 或完整 Provider 错误响应。

失败处理：

| 情况 | 处理 |
| --- | --- |
| Provider 未启用 | 直接进入人工验证 |
| 认证失败 `401/403` | 标记配置错误，停止自动重试并告警 |
| 限流 `429` | 在本次验证截止时间内指数退避 |
| `5xx`/网络故障 | 短暂重试，超时后转人工 |
| 响应超限或格式非法 | 立即终止解析，转人工并记录脱敏错误码 |
| 站点拒绝验证码 | 不循环提交同一验证码，重新取一次或转人工 |

自动失败降级时，同一注册任务只能存在一条活动的邮箱验证事项，避免 Worker 重试产生多条人工工单。

### 6.6 运行资源

路由：

- Worker；
- 代理；
- 执行会话。

默认进入 Worker。页面共享同一二级导航和运行状态摘要。

#### Worker

保留节点审批、暂停、维护、槽位和证书管理。节点详情保留资源使用与存储健康。

#### 代理

保留代理列表、健康状态、出口 IP、成功率和冷却状态。新增/删除代理仅超级管理员可用。

#### 执行会话

默认只显示活动会话；历史会话通过筛选查看。终止会话必须二次确认并要求填写原因。

### 6.7 待处理

待处理中心只汇集需要人做决定的事项：

#### 人工验证

- 邮箱验证码；
- 图片验证码；
- 风控确认；
- NAS/文件结果不确定。

#### 数据质量

- 待消歧作品；
- 疑似重复；
- 缺失关键字段；
- 需要人工合并/拆分。

删除直接填写“源 UUID / 目标 UUID”的合并表单。新的合并流程：

```text
选择疑似重复 → 并排比较版本/来源/馆藏 → 选择保留对象 → 确认影响 → 合并
```

#### 系统告警

- Worker 离线；
- 存储异常；
- 代理池不足；
- 导入失败；
- 索引延迟；
- 数据库或备份异常。

已解决事项默认不显示，可通过筛选查看历史。

### 6.8 系统管理

#### 操作日志

支持时间、级别、来源、操作人和目标筛选。日志详情使用抽屉，列表不展示过长文本。

#### 系统设置

设置按领域分组：

- 获取与重试；
- 账户与额度；
- 验证码接收；
- Worker 与租约；
- 存储；
- 导入与索引；
- 安全。

删除直接编辑任意键值的通用体验。已知设置应有明确名称、类型、范围、说明和验证；未知或高级键放入“高级设置”。

“验证码接收”设置仅超级管理员可编辑，提供 Provider 类型、启用状态、服务地址、超时、轮询间隔、发件人允许列表和人工降级开关。API Key 仅支持写入/更换，读取接口只返回“已配置”，不回显密文或明文。

页面显示 Provider 健康状态、配置版本、最近检查时间、脱敏错误和使用该版本的 Worker 数。“测试连接”只做认证与响应格式检查，不在前端展示邮件或验证码。

版本化配置的逻辑形态：

```yaml
mail_code:
  version: 7
  enabled: true
  provider: outlook_http
  base_url: https://outlook-mail.example.internal
  api_key_secret_ref: secret://outlook-mail/api-key
  poll_interval_seconds: 3
  timeout_seconds: 120
  sender_allowlist:
    - no-reply@example.com
  fallback: manual
```

Master 只持久化非敏感配置和 `api_key_secret_ref`。Worker 通过部署环境的密钥代理解析引用，密钥不放进普通配置下发消息。如现有环境没有密钥代理，上线 Outlook Adapter 前必须先提供等价的节点级密钥注入机制，不以明文数据库字段或 gRPC 字符串临时替代。

## 7. 前端模块设计

当前页面直接调用大量具体 HTTP 端点，容易让同一逻辑在多个页面重复。调整后按功能建立深模块。

建议目录：

```text
admin-web/src/
├── app/
│   ├── routes.tsx
│   ├── navigation.ts
│   └── permissions.ts
├── features/
│   ├── overview/
│   ├── library/
│   ├── acquisitions/
│   ├── imports/
│   ├── accounts/
│   ├── operations/
│   ├── attention/
│   └── system/
├── shared/
│   ├── http/
│   ├── table/
│   ├── forms/
│   ├── status/
│   └── layout/
└── legacy/
    └── redirects.tsx
```

### 7.1 `Library` 模块

外部接口：

```text
search(filters, cursor) -> SearchPage
getEdition(id) -> EditionDetail
```

实现内部隐藏搜索投影、分页、字段适配和错误恢复。列表页和详情页不直接拼接 HTTP 查询参数。

### 7.2 `Acquisitions` 模块

```text
list(filters, cursor) -> AcquisitionPage
apply(command) -> CommandResult
```

`command` 受控为重试、暂停、恢复、改优先级和确认，不为每个动作向页面暴露独立调用方式。

### 7.3 `Accounts` 模块

```text
listAccounts(filters, cursor) -> AccountPage
importAccounts(input) -> ImportResult
listRegistrations(filters, cursor) -> RegistrationPage
applyRegistration(command) -> CommandResult
```

账号池、注册队列和人工验证通过一个模块保持状态名称、权限和错误文案一致。

邮件验证码在 `automation-core` 设置一个稳定的 Seam，对外只暴露小型接口：

```text
prepare(email, deadline) -> MailCodeCursor
awaitCode(cursor, cancellation) -> MailCodeResult
health() -> ProviderHealth
```

接口的约束：

- `prepare` 在提交注册表单前执行，生成不透明游标；
- `awaitCode` 只能返回游标之后、未超过截止时间的验证码；
- 验证码长度限制为 4–8 位，结果不持久化；
- 取消注册任务必须立即取消轮询；
- 调用方只看到结构化结果和错误分类，不理解 Outlook 的 URL、响应 JSON 或重试细节。

具体 Adapter：

- `OutlookHttpMailCodeAdapter`：迁移旧 `/api/external/emails` 协议；
- `ManualMailCodeAdapter`：产生人工事项并等待 Master 回传；
- `MockMailCodeAdapter`：仅测试和非生产环境可用。

这三个 Adapter 让该 Seam 具有实际变化点。Worker 保持一个版本化 Provider Router：管理员更新配置后，新注册任务立即使用新 Adapter；已开始的注册尝试继续使用启动时的配置快照，避免中途切换造成验证码丢失。配置无效时拒绝切换并继续使用上一个健康版本。

### 7.4 `Attention` 模块

```text
getCounts() -> AttentionCounts
list(kind, filters, cursor) -> AttentionPage
resolve(command) -> ResolutionResult
```

导航角标、总览摘要和待处理页面共用同一个计数来源，避免多个页面显示不同数量。

### 7.5 共享表格模块

表格统一处理：

- 空状态；
- 加载骨架；
- 错误重试；
- 游标分页；
- 列宽和长文本；
- 批量选择；
- 权限控制；
- URL 筛选同步。

调用页面只描述列和业务动作，不重复实现分页与请求状态。

### 10.1 Outlook 接入安全约束

信任跨越点：

- 超级管理员浏览器 → Master 配置接口；
- Master → Worker 的版本化配置下发；
- Worker → `outlook-mail` 外部 HTTPS 服务；
- 外部邮件响应 → 验证码解析。

需要保护的资产是 API Key、账户邮箱、邮件内容、一次性验证码和注册任务控制权。

强制控制：

1. Provider 只允许 HTTPS；服务主机使用部署级允许列表，禁止回环、私网、链路本地和云元数据地址，禁止跨主机重定向，防止 SSRF。
2. API Key 由密钥管理或加密配置保管；数据库不存明文，前端与普通管理员不可读取，日志和错误中不得出现。
3. 配置新增、更换、启用、停用和测试连接均要求超级管理员权限并写入审计日志；审计记录只写配置版本和操作结果。
4. 邮件响应设置连接、总请求、轮询次数、单次响应大小和 JSON 字段长度上限；响应按不可信外部输入验证。
5. 只提取当前注册邮箱、允许发件人和时间窗内的 4–8 位验证码；不向 Master 上报邮件正文、主题或候选验证码列表。
6. 验证码只存在于 Worker 当前尝试的内存中，使用后立即丢弃，不入库、不进缓存、不写日志。
7. 健康检查和统计不使用真实验证码，指标标签不包含邮箱，避免 PII 和高基数标签。
8. Mock Adapter 在生产构建或生产配置中强制禁用，不能因配置错误返回固定验证码。

运行指标至少包含：

- `mail_code_fetch_total{provider,result}`；
- `mail_code_fetch_duration_seconds{provider}`；
- `mail_code_fallback_total{provider,reason}`；
- `mail_code_provider_config_version{node_id}`；
- `mail_code_provider_healthy{node_id,provider}`。

不允许将邮箱、账号 ID、注册任务 ID、验证码或邮件 ID 放入指标标签。

- 键盘、焦点、对话框和屏幕阅读器基础检查通过；
- Rust 单元测试覆盖 Provider 游标、解析、错误分类、取消和 Router 切换；
- 使用本地伪服务完成 Outlook 协议集成测试，测试不依赖真实邮箱或生产 API Key；
- 发布前进行依赖审计和密钥扫描，不存在未处理的可达严重/高危问题；
- 不出现旧页面与新页面数据状态不一致。

## 14. 上线与回滚

### 上线

1. 先上线新路由和旧路由重定向；
2. 开启简化导航；
3. 保留旧后端端点和历史批次只读视图；
4. 先以 Manual Adapter 上线新接口，确认人工降级闭环稳定；
5. 对少量 Worker 灰度启用 Outlook Adapter，观察取码成功率、延迟、降级率、`401/403`、`429` 和 `5xx`；
6. 扩大 Outlook 启用范围，但保留 Manual Adapter 和功能开关；
7. 观察一个正式版本的访问日志和操作错误；
8. 确认无人依赖旧入口后删除旧前端文件；
9. 后端清理由单独方案执行。

### 回滚

- 通过 `simplified_navigation` 恢复旧导航；
- 新旧路由同时存在于兼容期，不回滚数据库；
- 账号注册仍使用原后端表和调度逻辑，因此前端回滚不影响正在执行的注册任务；
- Outlook 出现错误率上升、认证故障或响应协议不兼容时，将活动 Provider 切换为 Manual，不回滚注册数据库状态；
- Provider 配置回滚到上一个已验证版本；已开始任务使用原配置快照完成或降级；
- 任何页面合并不得改变任务状态机或租约语义。

## 15. 验收标准

1. 一级导航不超过 8 项。
2. 首页只有一个，不再同时出现“运行总览”和“总库概览”。
3. 图书查询只有“图书总库”一个入口。
4. 图书下载只有“获取任务”一个入口，不出现可创建的新下载批次。
5. 补充书单从“数据导入”进入，并自动加入唯一全局获取池。
6. 账户注册功能完整保留，账号导入、注册队列、重试、验证码、额度和历史均可访问。
7. Outlook 自动取码接入云端 Worker，可在不重新编译且不中断图书下载的情况下切换 Provider。
8. Outlook 不可用时注册任务自动降级到人工验证，不丢任务、不重复创建人工事项。
9. API Key、邮件内容和一次性验证码不在前端、日志、指标、审计详情或数据库中泄露。
10. 前端不再要求用户理解“账号注册批次”，但后端调度和审计信息不丢失。
11. Worker、代理和会话在同一运行资源模块内可管理。
12. 人工验证、数据质量和告警在同一待处理模块内可下钻。
13. 旧路由在兼容期全部有明确跳转，不出现 404。
14. 所有查询和标签状态可通过 URL 恢复。
15. 旧页面删除后，复杂度不会重新散落到多个新页面；共享逻辑集中在对应深模块的接口后。

## 16. 最终决策摘要

- 删除旧图书、旧任务和下载批次前端；
- 总库概览成为唯一首页；
- 图书总库、获取任务和数据导入形成图书业务主线；
- 账户注册完整保留，并建立一级“账号中心”；
- 将旧单机程序的 Outlook 取码能力迁移到 Worker，通过 Provider Router 实现运行时热切换；
- Outlook 失败自动降级为人工验证，不让外部邮件服务成为注册队列的单点阻断；
- 验证码 Provider 的接口、密钥管理、SSRF 防护、脱敏、限流和审计作为强制验收项；
- 后端注册批次暂时保留，前端降级为注册分组；
- Worker、代理、会话合并为运行资源；
- 人工验证、数据质量、告警合并为待处理；
- 日志和设置合并为系统管理；
- 先做前端收敛和路由兼容，再单独评估后端清理。
